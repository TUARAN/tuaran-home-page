# Cloudflare 用量故障与优化记录

## 2026-11-02：D1 行读取到免费额度的 86%

- **口径**：2026-11-02 20:10 +0800 用账号 Analytics 核对 UTC 日 `2026-11-02`（北京时间 08:00 起）。账号合计读取 **4,301,922** 行、写入 18,158 行，占 Workers Free「每日 500 万行读取」的 **86.0%**。主库 `tuaran-me` 为 4,301,751 行；同账号其他库合计不到 200 行。查询分解来自 D1 Insights 最近 12 小时，和这个 UTC 日基本重合。
- **哪些任务在读**：
  1. 调研目录 `content_documents` 整表列出：2,586 次 × 约 401 行 = **1,039,112** 行，查询耗时约占这批高消耗查询的九成。文章页相关阅读、首页推荐、阅读量校验每次都把约 400 篇文档再读一遍。
  2. 社区动作中心的非 X 回执：`WHERE platform != 'x'` 用不上 `(platform, occurred_at)` 索引，41 次都扫完整张 `community_action_events`（每次 22,677 行），合计 **929,768** 行，实际只取最近 40 条。
  3. X 监控按账号看 7 日趋势：67 次 × 约 9,630 行 = **645,241** 行。日汇总表没有账号列，指定账号时只能扫该账号的动作明细。
  4. 游客目录分段统计：8 次 × 41,597 行 = **332,776** 行。`guest_stats` 只有总数，五个分段仍全表 `SUM`。
  5. 燃币公开供应量：6 次 × 约 41,532 行 = **249,192** 行，来自对 `user_points` 做 `COUNT` + `SUM(balance)`。
  6. 阅读量合格计数、消息中心未读列表也在后面，单次只有几千或一百多行，靠次数叠上去。
- **已改，部署后生效**：
  1. 公开调研目录在同一个 Worker 实例里缓存 5 分钟；后台内容列表仍每次读库。新发布或撤回最多晚 5 分钟出现在公开列表和阅读量校验里。
  2. 非 X 设备和回执改为按 `xhs`、`juejin` 等值查询后合并，走现有平台时间索引。
  3. 指定账号的监控汇总缓存 2 分钟；设备状态仍约 10 秒，回执列表仍约 1 分钟。
  4. 消息列表的总数和未读合并成一次扫描，去掉 `read_at IS NULL` 重复计算。
- **还没动，影响面更大**：游客分段和燃币余额要落到已有的单行汇总上，并在写入时维护；阅读量合格人数改成计数器；账号趋势要给 `community_action_daily_counts` 补账号列，或继续接受缓存失效后那一次约 1 万行扫描。这几项会改统计口径或写路径，这次没有一起改。

## 2026-10-28：D1 行读取偏贵的自查与收敛

- **口径**：Workers Free 的 D1「每日 500 万行读取」按**账号**计量，同账号下主站 D1 与 `china-poetry` 等库共用；计的是**扫描行数**，不是返回行数。UTC 0 点重置。
- **不合理点**：
  1. 插件云端历史同步 `readCommunityActionHistory` 曾一次 `LIMIT 6000`、回溯 365 天，且 `community_action_events` 缺 `(platform, account_handle, occurred_at)` 索引，过滤账号时容易多扫。
  2. 监控页按账号看趋势时对 events 做 14 天 `GROUP BY`，同样吃扫描行。
  3. 后台库表详情默认 `SUM(LENGTH(...))` 全表扫文本量；点开大表一次就可能几十万行读取。
  4. 每次 `/api/community-actions/report` 都读一次 `site_settings` 密钥（单行，但高频）。
  5. 常规链路曾把「监控心跳」和「次数/日报」绑在同一次高频 POST 上，动作成功也立刻打接口。
- **已改**：历史同步改为约 90 天 / 最多 500 条回执 + 120 条日报；账号趋势窗口 7 天；补索引 migration `0122`；表详情默认不算文本量（`?stats=full` 才算）；报告密钥同 isolate 内缓存 60 秒；**监控心跳约每分钟**（只带 runtime / 远端指令，不刷事件队列），**次数统计与日报约每小时**批量上传；设置页可手动「立即更新监控状态 / 立即同步次数统计」。
- **仍需注意**：旧版未限流插件会放大 Workers + D1；诗词库大 release / `COUNT(*)` 校验也占同一账号额度。额度耗尽后主站写库与 DB 控制台都会失败，与库损坏无关。

## 2026-10-26：Pages Functions 免费调用额度耗尽

- **观察**：2026-10-26 23:14 +0800 的 Cloudflare 账号 GraphQL 查询显示，当日 Workers 调用 119,054 次，其中公开站 Pages Worker `pages-worker--6819507-production` 113,451 次，超过免费套餐账号每日 100,000 次参考额度。`/login`、`/register`、`/api/auth/login` 返回 404，静态页面仍可访问。免费额度按 UTC 00:00 重置（北京时间 08:00）。同次查询显示 D1 当天读取 4,423,445 行、写入 53,105 行，不能把今日登录故障归因于 D1 写入额度。
- **主要入口**：同次查询显示 `/api/community-actions/report` 161,709 次入口请求，其中 86,669 次返回 200、74,853 次返回 405、187 次返回 503。405 多数发生在 Functions 不再运行时，因此入口请求数不能直接当作实际函数调用数。`/api/site-status` 当时 11,980 次（10,652 次 200、1,328 次 404），是次要来源。
- **原因**：X 插件 `content.js` 每秒渲染面板，等待倒计时也每秒变化；运行时状态因此反复更新，`background.js` 每次更新都触发远端心跳。每个心跳还会同步日报，并在服务端轮询远端指令。两台活跃 X 设备产生的请求量与该链路吻合。
- **本次修复**：远端任务详情改用稳定的等待状态和固定 `waitUntil` 时间戳，界面倒计时仍在本地显示；后台遥测增加每分钟一次的上限，回执模块对重叠的面板状态更新与闹钟心跳做 55 秒去重。每分钟闹钟仍负责远端指令轮询。正常状态下站点公告的浏览器轮询从每分钟改为每 5 分钟，隐藏标签页不再发请求；故障公告期间仍每分钟刷新。运行中心新增 Cloudflare 用量页，按 UTC 日归档 Workers 调用、D1 读写行数和高流量入口路径。
- **本地验证**：专项测试覆盖等待倒计时不改变远端详情、后台一分钟限频、重叠心跳去重、Cloudflare 用量归一化与 R2 快照读写，6 项通过。完整插件测试另有 1 条后台筛选按钮文案断言失败，失败位置与本次遥测改动无关。

## 2026-10-25：D1 用量异常

- **观察**：事后从 Cloudflare GraphQL 查询 2026-10-25 UTC 完整日，D1 读取 3,934,755 行、写入 134,672 行，写入超过 Free 套餐每日 100,000 行参考额度；读查询 95,250 次、写查询 52,998 次。账号 Workers 调用 71,792 次。`/api/community-actions/report` 有 26,734 次入口请求，其中 25,331 次返回 200、1,403 次返回 500。事后快照能确认全天量，无法单靠它确定当天首次触顶的时刻。
- **已上线的处理**：2026-10-26 09:15 +0800 的提交 `c2d367b8` 为 `community_action_devices` 心跳写入加了 3 分钟条件，并限制 `x_extension_runtime` 的重复写入。这个改动减少了相同心跳的 D1 写入，但仍会对每次报告执行鉴权和远端指令查询。
- **后续观察**：2026-10-26 23:14 +0800 的当日部分统计为 D1 写入 53,105 行、读取 4,423,445 行。两天流量结构和时间窗口不同，不能把总量差直接归因于 3 分钟写入节流。新每日快照上线后，应比较 D1 每日读写行数、查询次数及 X 插件报告量。

数据口径：Workers 调用取 Cloudflare 账号 GraphQL 的 `workersOverviewRequestsAdaptiveGroups`；路径入口量取区域 `httpRequestsAdaptiveGroups`；D1 行数和查询次数取 `d1AnalyticsAdaptiveGroups`。这些口径不同，不可直接相加。
