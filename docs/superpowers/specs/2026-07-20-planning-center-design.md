# 后台规划中心设计

日期：2026-07-20  
状态：已确认，待实施计划

## 1. 背景

当前后台已经具备项目台账、本站开发看板、AI 任务、上下文记忆和近期变更等能力，但项目的过去、现在与未来分散在多个入口：

- 过去主要存在于主站 Changelog、Git 提交、完成事项和项目归档中。
- 现在主要存在于项目台账、本站开发看板、GitHub Issue/PR 和 AI 任务中。
- 未来主要存在于项目 `next_step`、里程碑字段和零散规划文本中。

规划中心要把这些信息收束为全部项目组合的统一规划正本。它不是另一个孤立的待办页，而是从战略方向到具体任务的管理入口，并通过事件与决策档案持续沉淀项目历史。

## 2. 产品目标

规划中心覆盖全部项目组合，包括 2aran、博主联盟、前端周刊和 AI Agent 等项目线。

它需要同时满足三个目标：

1. 以统一规划正本的方式维护方向、项目、里程碑和任务。
2. 汇总现有项目数据，并为未来的 GitHub、提醒、复盘和 AI 能力保留连接点。
3. 保存关键事件、决策和复盘，使项目为何变化、如何走到今天可以被追溯。

首版成功标准是形成完整的本地规划闭环：用户能建立规划、推进任务、识别风险、完成事项并自动形成历史，而不依赖外部系统。

## 3. 已确认的产品原则

- 规划中心是规划数据的唯一正本。
- GitHub 等外部系统在后续版本中只作为关联与进度信号，不反向成为主数据源。
- 项目身份和商业属性继续由现有 `portfolio_projects` 管理，规划中心不复制项目基本资料。
- 历史采用“自动沉淀 + 手动补充”：状态变化自动生成事件，同时允许补录历史、决策和复盘。
- 时间采用滚动时间窗：过去按时间线归档；现在聚焦本周、本月和本季度；未来分近期、中期和长期。
- 首版只交付核心闭环，不包含 GitHub 同步、通知提醒、AI 总结、多用户协作或公开展示。

## 4. 信息层级

规划层级为：

```text
方向 → 项目 → 里程碑 → 任务
```

### 4.1 方向

方向表达一组项目共同服务的长期目标，例如个人门户、博主联盟、前端周刊和 AI Agent。方向包含愿景、生命周期状态、优先级、时间范围和当前季度北极星描述。

### 4.2 项目

项目引用 `portfolio_projects.id`。项目名称、板块、路径、商业状态、收入和投入等资料继续从项目台账读取。首版中每个项目只归属一个主方向，避免引入多方向归属的额外复杂度。

### 4.3 里程碑

里程碑属于一个项目和对应方向，表达阶段性、可验证的结果。它包含目标、成功标准、状态、优先级、开始日期、目标日期和完成日期。

### 4.4 任务

任务必须属于一个里程碑。任务包含标题、说明、状态、优先级、计划时间、开始时间、完成时间、备注和阻塞原因。首版只有站长本人使用，因此负责人字段默认为站长，不建设成员目录或协作分派能力。

## 5. 页面架构

规划中心位于 `/admin/planning`，加入后台“项目与工程”工作台及主导航。页面包含四个视图。

### 5.1 三时态总览

这是默认首页，以“过去、现在、未来”三栏为骨架。

顶部展示：

- 当前季度北极星方向。
- 本期完成数量。
- 当前焦点数量。
- 风险与待决策数量。
- 方向筛选及本周、本月、本季度时间窗。

三栏内容：

- 过去：已完成、已取消事项，以及历史事件、决策和复盘。
- 现在：进行中、阻塞中、逾期未完成及当前焦点窗内的事项。
- 未来：尚未开始的计划，按近期、中期、长期和待排期分组。

首页卡片只展示判断所需的摘要。点击卡片后逐层进入项目、里程碑和任务详情，避免在总览堆叠完整表单。

### 5.2 组合路线图

组合路线图按项目横向比较季度节奏、里程碑和跨项目依赖。它用于识别资源冲突、延期传导和不同项目之间的先后关系，不替代三时态首页的日常推进功能。

### 5.3 规划树

规划树完整呈现方向、项目、里程碑和任务层级，是结构维护和批量浏览入口。新增、编辑、归档和调整优先级均可从这里完成。

### 5.4 历史与决策

该视图按时间线展示自动事件、手工历史、复盘和关键决策。用户可以按方向、项目、事件类型和时间范围筛选。

决策记录包括：

- 背景与待解决问题。
- 最终结论。
- 判断理由。
- 影响范围。
- 关联方向、项目或里程碑。
- 决策日期。

## 6. 核心交互

### 6.1 快速添加

页面提供统一“快速添加”入口，可创建方向、里程碑、任务、历史事件或决策。入口根据当前筛选和所在详情页预填方向、项目或里程碑；任务提交前必须明确选择所属里程碑。

### 6.2 状态驱动流转

- 新建且尚未开始的里程碑或任务进入未来。
- 状态变为进行中或阻塞时进入现在。
- 逾期但未完成的事项仍留在现在，并显示风险提示。
- 状态变为完成或取消时退出现在，并在过去生成对应事件。
- 没有计划日期的未开始事项进入未来的“待排期”。

### 6.3 完成约束

里程碑存在未完成任务时，系统默认阻止直接完成，并展示仍需处理的任务。用户需要先将这些任务完成、取消或移动到其他里程碑。

### 6.4 归档与删除

未被引用且没有历史的误建记录可以删除。已经存在子项、依赖、决策或事件的记录只能软归档。历史事件不可物理删除；人工补录错误通过更正事件说明，不静默改写原始记录。

## 7. 数据模型

首版采用普通关系表保存当前状态，用只追加事件表保存变化历史，不使用完整事件溯源架构。

### 7.1 `planning_directions`

保存方向的名称、愿景、状态、优先级、时间范围、北极星描述、排序和审计时间。

建议状态：`planned`、`active`、`paused`、`completed`、`archived`。

### 7.2 `planning_project_profiles`

保存规划域对现有项目的引用，包括 `project_id`、`direction_id`、规划状态、焦点标记、排序和审计时间。`project_id` 唯一，首版保证一个项目只有一个主方向。

### 7.3 `planning_milestones`

保存 `direction_id`、`project_id`、标题、目标、成功标准、状态、优先级、开始日期、目标日期、完成日期、来源标识、排序和审计时间。

建议状态：`planned`、`active`、`blocked`、`completed`、`cancelled`、`archived`。

### 7.4 `planning_tasks`

保存 `milestone_id`、标题、说明、状态、优先级、负责人、计划日期、开始日期、完成日期、备注、阻塞原因、排序和审计时间。

建议状态：`planned`、`doing`、`blocked`、`done`、`cancelled`、`archived`。

### 7.5 `planning_events`

保存实体类型、实体 ID、事件类型、标题、说明、发生时间、来源、来源唯一键和创建时间。该表只追加，不被实体归档或删除级联清理。

建议事件类型：`created`、`started`、`blocked`、`completed`、`cancelled`、`decision`、`review`、`note`、`imported`、`corrected`。

### 7.6 `planning_decisions`

保存标题、背景、结论、理由、影响、决策日期，以及可选的方向、项目和里程碑关联。

### 7.7 `planning_dependencies`

保存来源实体、目标实体、依赖类型、说明、状态和审计时间。首版允许里程碑或任务之间建立阻塞与依赖关系，并支持跨项目关联。

## 8. 数据流与一致性

读取总览时，服务端按方向和滚动时间窗查询里程碑、任务、事件和决策，再计算三时态分组、风险数量和待决策数量。

写入时遵循以下规则：

1. API 验证站长身份、父级存在性、状态值和日期范围。
2. 当前记录更新与对应历史事件在同一 D1 事务中完成。
3. 客户端收到成功结果后刷新受影响的总览、路线图和详情数据。
4. 保存失败时保留表单输入，显示可读错误并允许重试。

过去视图以事件发生时间为依据，不根据当前字段反推历史。现在与未来视图根据当前状态、计划日期和所选滚动时间窗动态计算。

## 9. 初始化迁移

初始化通过仅站长可见的一次性导入流程完成，导入前显示预览和预计新增数量。

### 9.1 方向与项目

- 根据现有项目台账的四条主线创建初始方向。
- 为全部 `portfolio_projects` 创建规划引用，不复制项目名称和商业字段。
- 项目与方向的映射使用现有 `pillar` 作为初始值，导入后由规划中心维护。

### 9.2 `next_step`

每个非空 `next_step` 导入为该项目下的“待确认、待排期”里程碑。导入记录保留来源标识，用户确认后可重命名、补充成功标准并排期。

### 9.3 Changelog

每一期 Changelog 导入为 2aran 项目的一条历史事件，事件说明保留该期完成项和规划项。首版不把每个项目符号拆成独立任务，避免制造大量缺少上下文的记录。

### 9.4 幂等性

每条导入记录使用稳定的来源唯一键。重复运行只跳过已存在记录，不更新已经在规划中心编辑过的数据。完成初始化后，旧数据源不会持续自动同步。

## 10. 权限、异常与边界

- 页面沿用现有 `AdminPageGate`，接口沿用后台站长鉴权。
- 未授权请求返回明确的 401 或 403，不泄露规划数据是否存在。
- 父级缺失、非法状态、无效日期和循环依赖返回可读的 400 错误。
- 目标日期早于开始日期时拒绝保存；实际完成日期可以晚于目标日期。
- 已归档父级不可新增子项。
- 空状态提供明确的首个动作，不显示伪造数据。
- 总览某一部分加载失败时保留其他已成功区域，并提供局部重试。
- 首版不向 GitHub 或任何外部服务写入数据。

## 11. 测试与验收

### 11.1 数据与规则测试

- 三时态自动归类覆盖计划、进行中、阻塞、逾期、完成、取消和待排期。
- 状态更新与事件写入保持原子性。
- 软归档不会丢失历史、决策和依赖。
- 循环依赖被拒绝。
- 初始化导入可重复运行且不产生副本。

### 11.2 API 测试

- 方向、项目规划资料、里程碑、任务、事件、决策和依赖的 CRUD。
- 父级、状态、日期和完成约束校验。
- 未授权与非站长访问被拒绝。
- 导入预览、执行和幂等结果正确。

### 11.3 界面验收

- 三时态总览、组合路线图、规划树、历史与决策均可访问。
- 方向与时间窗筛选结果正确。
- 快速添加能继承当前上下文并在失败后保留输入。
- 风险、阻塞、逾期和待排期有清晰区分。
- 空状态、加载失败、保存失败和局部重试可用。
- 桌面端与移动端布局可用，键盘焦点和表单标签完整。

### 11.4 项目验证

- 新增数据库迁移可安全执行。
- 后台专项构建验证通过。
- 全站 lint、样式检查和相关构建检查通过，或明确记录与本功能无关的既有失败。

## 12. 首版不包含

- GitHub Issue、PR 或提交的自动同步。
- 外部系统双向写入。
- 通知、提醒和日历联动。
- AI 自动总结、规划建议或复盘生成。
- 多用户协作、任务分派和权限矩阵。
- 面向主站访客的公开路线图。

这些能力只能在首版核心闭环稳定后，通过独立设计和实施周期增加。

## 13. 后续演进

首版之后可以按以下顺序演进：

1. GitHub 只读关联，为任务显示 Issue、PR 和提交信号。
2. 周期复盘与提醒，将滚动时间窗转化为固定节奏。
3. AI 总结与风险建议，但不允许 AI 静默修改规划正本。
4. 根据实际需求评估多用户协作或公开路线图。
