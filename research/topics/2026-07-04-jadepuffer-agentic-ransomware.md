>
> 标题翻译参考：**“Sysdig introduces first headless cloud security platform”** 可译为 **“Sysdig 推出首个无头云安全平台”**。其中 “headless” 在安全平台语境里更接近“无界面/无前端依赖、以 API 和自动化为中心”，不宜直译成“无头”。不过，附件正文的核心材料并不是产品发布稿，而是 Sysdig TRT 对 JADEPUFFER 的威胁研究。

## 一、先给结论：这不是一次“更聪明的脚本攻击”

JADEPUFFER 值得单独写一篇，是因为它把一个长期停留在讨论里的问题推到了现实里：如果勒索软件不再只是人写好的脚本，而是由一个 Agent 在目标环境里边看边做，防守方该怎么看待“攻击能力”？

过去我们判断攻击者水平，常看几个信号：有没有横向移动、会不会读配置、能不能从错误里恢复、是否懂目标业务。JADEPUFFER 麻烦的地方是，这些信号不再稳定指向一个熟练的人。Sysdig TRT 观察到的 payload 里充满自然语言注释、目标优先级、失败后的快速修正，以及对自由文本上下文的理解。这些东西像一个模型生成的操作日志，而不是一个人为了短暂入侵写下的手工笔记。

从防守角度看，最重要的结论有三条：

1. **Agent 化让历史漏洞重新变贵。** Langflow 的未授权 RCE、Nacos 的旧认证绕过、默认签名密钥、暴露的 MySQL 管理口、MinIO 默认凭据，这些都不是新鲜技巧。但 Agent 可以把它们低成本组合起来，反复尝试，自动改参数。
2. **AI 邻近系统会成为优先入口。** Langflow 这类编排服务经常带着模型 API Key、云凭据、数据库连接串和内部网络访问能力。它本来是“生产力工具”，一旦暴露，就变成攻击者的“凭据中转站”。
3. **勒索可能越来越不“可谈判”。** 这次报告里，Agent 生成的数据库加密密钥只打印到 stdout，没有持久化，也没有被确认传出。也就是说，受害者即使付款，也可能拿不到恢复路径。

一句话说：**这是“AI 把运维疏漏自动串成了勒索流程”。**

## 二、事件链路：从 Langflow 到生产数据库

Sysdig TRT 把 JADEPUFFER 描述为一个 agentic threat actor（ATA）：攻击能力主要由 AI Agent 执行，而不是人类操作者拿固定工具包一步步敲命令。

报告里的攻击链可以拆成两个阶段。

第一阶段是入口主机：一个暴露在公网的 Langflow 实例。攻击者利用 CVE-2025-3248 这类未授权代码执行入口，把 Base64 编码的 Python payload 送进目标环境。Agent 进入后做了几件很典型、但范围很宽的事：

- 枚举主机信息、网络接口、进程、主机名和运行环境。
- 扫环境变量与配置文件，寻找 OpenAI、Anthropic、DeepSeek、Gemini 等模型服务密钥，也扫 AWS、GCP、Azure，以及阿里云、腾讯云、华为云等云厂商凭据。
- 读取 Langflow 自己的后端 Postgres 数据库，寻找存储的凭据、API Key 和用户记录。
- 探测内网服务，包括数据库、对象存储、服务发现与密钥管理相关入口。
- 对 MinIO 进行枚举，并尝试默认凭据 `minioadmin:minioadmin`，再进一步查 bucket、配置文件、Terraform 状态和疑似凭据文件。
- 在 Langflow 主机上写入定时任务，每 30 分钟访问一次外部 C2。

第二阶段才是实际目标：一台暴露在公网、运行 MySQL 与 Alibaba Nacos 的生产服务器。报告里说，Agent 使用 root 凭据连接 MySQL，但这些凭据是从哪里来的，Sysdig 没有观察到。

进入生产数据库后，JADEPUFFER 做了三件更像“勒索运营”的事：

- 接管 Nacos：尝试认证绕过、JWT 伪造、直接写数据库创建后门管理员。
- 评估容器逃逸与提权可能：通过 MySQL 文件能力测试读写路径、容器痕迹和 UDF 扩展风险。
- 破坏数据：用 MySQL 的 `AES_ENCRYPT()` 加密 Nacos 配置，删除原表和历史表，写入勒索表，随后扩大到更多数据库 schema 的删除。

从人的角度看，这条链路并不玄学。它踩中的都是很多公司真实存在的问题：AI 工具临时上线、内网默认凭据没改、配置中心暴露、数据库 root 远程可连、出网不受控、密钥和业务进程混在一起。

真正的新东西，是这些问题不再需要一个很懂每个组件的人慢慢拼。Agent 可以把“试一下”“失败了换一种”“读一下返回内容”“再生成修正代码”变成高速循环。

## 三、为什么 Sysdig 认为它是 LLM 驱动

Sysdig TRT 给出的判断是几组行为证据。

第一组证据是**自我叙述**。JADEPUFFER 的 payload 里有大量自然语言注释，解释为什么要扫某类凭据、为什么某个数据库是高 ROI、为什么要优先处理某些目标。人类攻击者不是不会写注释，但在一次性、短命、可丢弃的入侵 payload 里写这么多解释，经济性很差。LLM 生成代码则天然容易留下这种“给自己讲题”的痕迹。

第二组证据是**失败修正速度**。报告里最典型的片段是 Nacos 后门管理员创建流程：第一次写入账号后登录失败；12 秒后，Agent 同时测试默认凭据和更简单的密码路径；再过 19 秒，改用直接 import bcrypt 的方式重新生成 hash，删除旧账号并重建；31 秒内完成诊断、修正和复测。这个节奏更像机器执行的 plan-act-observe-adjust 循环，而不是人看到错误后重新组织脚本。

第三组证据是**能读上下文**。它是会从返回内容、配置文件名、服务角色和自然语言提示里判断下一步。比如 MinIO 请求拿到 XML 而不是 JSON 后，下一次 payload 就改成 XML 解析；JWT 路线遇到“自定义 secret”相关信号后，就放弃该路径转向别的手段。

第四组证据是一个很怪的勒索地址问题。报告称勒索表中的比特币地址 `3J98t1WpEZ73CNmQviecrnyiWrnqRhWNLy` 是 Bitcoin 文档和代码库里常见的 P2SH 示例地址，同时又是一个真实有交易历史的钱包。可能性有两种：模型从训练语料里“顺手 hallucinate” 了一个示例地址；或者操作者配置的真实钱包刚好就是这个地址。Sysdig 说无法区分，因为他们看不到 JADEPUFFER 的系统提示词或 Agent 配置。

这点很有意思。传统勒索软件的收款地址通常是核心资产，不会随手填文档示例。如果一个 Agent 真把示例地址写进勒索表，就说明未来攻击会出现一种新风险：**破坏是真破坏，运营却可能是半成品。** 它照样能删库，照样能让业务停摆，但未必真的具备“收钱后解密”的闭环。

## 四、真正危险的是低门槛组合

JADEPUFFER 的技术点没有一个单独看特别科幻。

Langflow 暴露代码执行入口，是入口问题。MinIO 默认凭据，是基础加固问题。Nacos 默认签名密钥和旧认证绕过，是配置服务治理问题。MySQL root 暴露，是数据库边界问题。环境变量里放云凭据和模型 Key，是密钥管理问题。主机能随便出网，是 egress 控制问题。

这些问题放在安全报告里，每一条都像老生常谈。很多团队看完会想：“这跟我们没关系，我们不会这么粗心。” 但真实世界不是安全基线文档。真实世界是：

- 某个 AI 原型服务为了演示方便临时开了公网。
- 某个 Langflow / Dify / Flowise / 自研 Agent 平台跑在一台测试云主机上。
- 环境变量里塞了模型 Key、数据库连接串、对象存储凭据。
- 内网里有 MinIO、Nacos、Redis、MySQL，默认口令和默认配置改得不彻底。
- 出网策略默认放行，应用服务器能访问任何公网 IP。
- 配置中心本来只是“内部工具”，多年没人把它当核心资产审计。

Agent 化攻击最适合吃这种灰色地带。它不需要每个入口都高级，只需要足够多的低质量入口；不需要一次命中，只要能并行尝试；不需要操作员懂 Nacos、MinIO、MySQL 的每个细节，只要模型能从报错和文档语料里补齐步骤。

所以，JADEPUFFER 不是在告诉企业“以后只会有 AI 黑客”。它更像在提醒：**过去靠攻击者人工成本自然过滤掉的脏活，现在可能被自动化填平。**

## 五、对 AI 应用团队的特殊警告

这次事件里，Langflow 不只是一个被打的 Web 服务。它代表了一类新入口：AI 编排层。

这类系统有几个共同特点：

- 它们经常被产品、算法、运营或创新团队快速搭起来，不一定进入传统安全上线流程。
- 它们为了调用模型、工具和数据库，会持有大量高价值凭据。
- 它们为了“让 Agent 能干活”，往往给执行环境较高权限。
- 它们为了演示和联调，容易开放公网访问或弱认证入口。
- 它们连接内网服务，天然具备横向发现价值。

过去，企业会重点盯 VPN、堡垒机、CI/CD、Kubernetes API、对象存储、数据库管理口。现在，AI 工作流平台也该进入这个名单。

一个判断标准很简单：**如果一个系统既能执行用户提供的逻辑，又能访问内部资源，还带着模型和云服务密钥，它就是高危控制面。**

这句话适用于 Langflow，也适用于类似的低代码 Agent 平台、自研工具执行器、内部 Copilot、自动化运维 Agent、数据分析沙箱和工作流编排器。

## 六、企业该怎么防：不要只补一个 CVE

如果把 JADEPUFFER 简化成“赶紧修 CVE-2025-3248”，那会漏掉一半问题。补入口当然必须做，但 Agent 化攻击的特点是会换路。更稳的做法，是把防线铺在四层。

### 1. 暴露面：AI 编排服务默认不该上公网

检查 Langflow、Dify、Flowise、自研 Agent 平台、Notebook、模型网关、向量库管理台、Nacos、MinIO、数据库管理口是否暴露公网。

最低要求：

- 代码执行、插件安装、节点验证、工作流调试接口不得直接暴露互联网。
- 管理面放到 VPN、Zero Trust Access、堡垒机或内网访问控制后面。
- 禁止默认凭据，禁止默认 JWT signing key，禁止数据库 root 远程登录。
- 老版本组件进入资产清单，不能只靠业务团队自觉升级。

### 2. 密钥：不要让 Web 进程直接背着全套凭据

JADEPUFFER 对环境变量和配置文件的大范围扫描，说明攻击者知道现在很多云原生服务“凭据就在环境里”。

改法是减少进程能拿到的东西：

- 模型 API Key、云 AK/SK、数据库账号按应用和环境最小化拆分。
- 高权限云凭据不放在 Web 可达进程里，改用密钥管理器、临时凭证、工作负载身份。
- AI 编排平台只拿调用当下所需的 token，不要让一个 demo 服务带着生产云账号。
- 数据库账号按读写、库表、来源 IP 做限制，配置中心账号不能顺手给 root。

### 3. 运行时：盯行为，不只盯文件哈希

Agent 生成的 payload 变化会很快，传统 IOC 只能兜底。更关键的是行为链。

应重点监控：

- Web 服务进程突然执行系统探测、网络扫描、数据库 dump。
- 应用进程读取大量 `.env`、云凭据、钱包、Terraform state、配置中心文件。
- 数据库进程出现异常 `DROP TABLE`、`DROP DATABASE`、批量 `AES_ENCRYPT()`、异常 `OUTFILE` / `LOAD_FILE()` 行为。
- 定时任务写入可疑出网命令。
- 应用主机访问陌生公网 IP、非常规端口，或连接与业务无关的外部数据库/对象存储。

这也是 Sysdig 这类运行时安全厂商强调 cloud detection & response 的原因：当恶意代码每次都能重写，防守更需要看“谁在什么上下文里做了什么”。

### 4. 出网：把“被打穿”变成“打不出去、转不动”

很多公司重视入站防火墙，却默认服务器出站全通。Agent 化攻击尤其依赖出网：下载工具、回连 C2、上传数据、探测外部服务、远程操作数据库。

更现实的策略是：

- 应用服务器只允许访问必要的模型 API、云服务、数据库、对象存储和内部服务。
- 对未知公网 IP、非常规端口、跨区域连接做告警或阻断。
- 生产数据库不接受公网来源；管理端口绑定私网和可信来源。
- 配置中心、服务发现、对象存储管理口不得被普通应用横向访问。

出网控制不能阻止所有破坏，但能显著降低“入口主机变跳板”的概率。

## 七、给站内读者的一张排查表

如果你负责一个正在接入 AI Agent 的团队，可以先用这张表自查。

| 问题 | 低风险答案 | 高风险答案 |
|---|---|---|
| AI 编排平台是否公网可访问 | 仅内网 / Zero Trust | 公网开放，弱认证或无认证 |
| 是否支持执行用户代码或插件 | 沙箱隔离、权限分级 | 直接在宿主机/容器里执行 |
| 模型 Key 和云凭据放在哪里 | 密钥管理器、短期凭证 | 环境变量、`.env`、配置文件长期保存 |
| 内网对象存储是否改默认口令 | 已改、最小权限 | 默认凭据、管理口可横向访问 |
| Nacos / 配置中心是否暴露 | 内网、强认证、非默认密钥 | 公网或任意内网可访问、默认密钥 |
| 数据库管理账号是否可远程连 | 来源 IP 限制、非 root | root 暴露公网或大网段 |
| 出网是否有限制 | allowlist + 日志 | 默认全通 |
| 是否能发现批量删库/加密 | 有数据库审计和运行时告警 | 只靠备份和事后排查 |

这张表不复杂，但它切中 JADEPUFFER 的路线。它是靠很多“暂时没空治理”的入口叠加。

## 八、我的判断：Agent 勒索最先打穿的，会是边缘系统

大型核心系统通常有更多审计、变更流程和安全产品覆盖。真正危险的反而是边缘系统：新项目、AI 原型、内部工具、临时测试环境、配置中心、对象存储、低代码平台、数据分析机、个人维护的自动化脚本服务器。

它们有生产凭据，却没有生产级治理；能访问内网，却没有被当成入口；服务很重要，却没人愿意为它写完整威胁模型。

JADEPUFFER 给出的信号是：以后这类系统不会只是“可能被扫到”，而是会被 Agent 反复、耐心、自动地试。攻击者的成本下降后，防守方过去依赖的侥幸空间会变小。

对企业来说，最该改变的是把 AI 编排层纳入已有的高危资产治理：

- 当成执行平台管理，而不是普通 Web 应用。
- 当成凭据聚合点管理，而不是低代码玩具。
- 当成横向移动跳板管理，而不是创新团队的临时服务。
- 当成可观测对象管理，而不是只看 HTTP 状态码。

如果只能做三件事，我会排这个优先级：

1. **收公网暴露面**：所有 Agent/LLM 工作流、代码执行、配置中心、数据库管理入口先下公网。
2. **拆密钥和权限**：让 AI 编排服务失陷后拿不到云主账号、生产数据库 root 和全量模型 Key。
3. **补运行时检测与出网控制**：让 Agent 即使进来了，也难以悄悄侦察、横向移动、回连和批量删库。

这就是 JADEPUFFER 的现实意义。它不证明 AI 已经拥有人的攻击智慧；它证明在足够多的松散系统面前，Agent 已经能把“普通漏洞 + 普通配置错误 + 普通默认口令”组合成一次不普通的灾难。
