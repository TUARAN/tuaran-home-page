本文讨论 2aran.com 站内的燃币、文章 / 资料解锁和工具包下载，不涉及现金充值、提现或法币支付。文中“缓存”指 Workers isolate 内存中的短缓存；它是读优化，不承担权限正本。

## 一、先给结论

燃币系统里的数据应该按“变更频率”和“错误代价”拆开处理。

| 数据 | 真相源 | 是否缓存 | 当前建议 |
|---|---|---:|---|
| 全站燃币规则 | D1 `site_settings` | 是 | Edge 内存缓存 45 秒 |
| 单资源覆盖价格 / 最低角色 | D1 `gated_resources` | 是 | 按 `resource_key` 缓存 60 秒 |
| 用户余额 | D1 `user_points` + `point_ledger` | 否 | 每次实时读写 |
| 用户是否已解锁 | D1 `resource_unlocks` | 否 | 每次实时判断 |
| 扣款、账本、解锁记录 | D1 | 否 | 每次走数据库，保留幂等键与审计 |

这套分法解决了两个相反的要求：站长可以在后台修改“阅读一篇内容扣多少燃币”“工具包默认多少燃币”，而用户不能因为某个边缘实例的旧内存、或缓存里的旧余额，多拿一次权益。

当前站内采用的具体 TTL 是：规则 45 秒，资源覆盖配置 60 秒。保存后台规则后，写入 D1 并清掉当前 Worker isolate 的规则缓存；其他已经运行的 isolate 不需要互相广播，最多在各自 TTL 结束前短暂沿用旧规则。对价格这种低频运营配置，这个传播窗口可接受，也换来了更少的 D1 查询和更简单的运行结构。

## 二、问题从哪里来：价格不能继续写死在代码里

燃币的早期实现通常从几个常量开始：注册奖励 100、签到 5、内容阅读 5、工具包下载 10。它能很快跑起来，但运营一旦想改价，就会遇到三个问题。

第一，改一个数字要发版。价格原本是运营规则，却变成了工程发布流程的一部分。第二，页面文案、API 判断、后台说明很容易各自保留一份数字，最后出现“后台写 10、实际扣 5”的情况。第三，给某一个工具包、文章或资源单独定价时，常量体系没有合适的位置。

因此，规则需要从代码中抽离：全站默认规则放在 `site_settings` 的 `ranbi.*` 键下，资源的例外规则放在 `gated_resources`，通过 `resource_key` 覆盖默认价和最低角色。代码常量仍保留一份，但只作为首次部署、D1 未绑定或旧数据缺失时的兜底，不再是日常运营的配置入口。

| 配置层级 | 例子 | 适用场景 |
|---|---|---|
| 全站默认规则 | `ranbi.researchDefaultCost = 5` | 调研文章没有单独配置时的解锁价 |
| 类型默认规则 | `ranbi.toolDefaultCost = 10` | 工具包 / 安装包没有单独配置时的下载解锁价 |
| 单资源覆盖 | `resource:x-mutual-cleaner-extension = 15` | 某个插件、桌面应用或资料需要特殊定价 |
| 用户权益数据 | `resource_unlocks` 的一条记录 | 某位用户已经解锁，之后永久可读 |

“内容”与“资源”不必在产品名称上争论。系统只需要把可收费对象分成可识别的资源键：文字内容默认走内容价；真正交付安装包、插件或工具的下载入口默认走工具价；壁纸、音乐等免费资源仍记录访问 / 下载事件，但成本为 0。价格和记录是两件事，免费不等于不留痕。

## 三、数据结构：把配置、资产和用户事实分开

一个容易维护的实现至少要有四类数据。

| 数据表 / 概念 | 保存什么 | 为什么不能混在一起 |
|---|---|---|
| `site_settings` | 全站规则、更新时间、操作者 | 规则少、读取频繁、由后台集中维护 |
| `gated_resources` | `resource_key` 的覆盖价、最低角色 | 只对特定资源生效，不能反过来污染全站默认价 |
| `point_ledger` | 每一次获得、使用、人工调整的流水 | 账本用于审计，不应被余额覆盖掉 |
| `user_points` / `resource_unlocks` | 当前余额、已解锁权益 | 它们是用户事实，直接参与授权判断 |

余额可以作为账本的物化结果使用，但不能把“余额缓存”误当成账本。用户投诉“我为什么少了 10 燃币”时，排查入口应当是 `point_ledger`；用户问“我是否已购买这个插件”时，排查入口是 `resource_unlocks`。这比只维护一个不断覆盖的余额字段可靠得多。

## 四、读路径：缓存只碰低风险、低频变更的数据

一次资源解锁请求可以拆成两条路径。

```text
价格与规则：Edge 内存命中 → 直接使用
                  ↓ 未命中或过期
                查询 D1 → 写入 45 / 60 秒短缓存

用户事实：读取余额、已解锁状态 → D1
                  ↓
             判断余额与角色 → D1 写账本 / 余额 / 解锁权益
```

实现上，全站规则缓存使用一个 isolate 内的对象，并用一个 `loading` Promise 合并同一时刻的首次回源，避免多个并发请求一起查询同一组 `ranbi.*` 键。单资源覆盖价则以 `resource_key` 为 key 放进 `Map`，连“该资源没有覆盖配置”这个空结果也短暂缓存，避免反复查询不存在的例外。

```js
// 示意代码：规则缓存命中后不读 D1；缓存失效再回源。
if (rulesCache?.expiresAt > Date.now()) return rulesCache.rules

const rules = await readRulesFromD1()
rulesCache = { rules, expiresAt: Date.now() + 45_000 }
return rules
```

这里的关键是缓存对象的选择。规则的变更频率低，短暂读到旧值的影响可以被明确限制；余额与解锁状态则可能在上一毫秒刚变化，缓存命中反而会造成多扣、少扣或错误放行。

## 五、写路径：先写 D1，再让缓存自然收敛

管理员保存一套规则时，顺序应固定：校验输入、写入 D1、清除当前 isolate 缓存、返回新规则。不能先删缓存再尝试写库；写库失败后，下一次读可能又把旧规则重新加载，界面会给人一种“保存过了”的错觉。

资源覆盖规则同理。新增、修改或删除 `gated_resources` 的某个 `resource_key` 后，立即清掉当前 isolate 中这个 key 的缓存。代码还需要防止一个较早发出的查询在稍后返回时，把刚被后台修改的旧值重新写回缓存；做法是给每个 key 维护一个递增版本号，只有版本未变化的查询结果才允许落入缓存。

不同边缘实例之间没有共享进程内内存，因此后台保存不能瞬间清空所有实例。这里接受“最多一个 TTL 的最终一致”，同时把 TTL 控制在一分钟以内。对于一条高风险的临时改价或紧急下架，运营应改用更强的策略：直接关闭资源、让交付接口实时查状态，或进一步引入集中协调层。

## 六、为什么不把这些数据放进 Workers Cache API 或 KV

Workers 的 isolate 内存不是永久进程内存。Cloudflare 明确说明，运行 isolate 可能被驱逐；全局可变状态只能作为尽力而为的优化，不能作为可靠持久化机制。这个限制恰好符合本方案的定位：内存缓存消失只会多查一次 D1，不会丢失规则或改变用户权益。 [Workers 运行模型](https://developers.cloudflare.com/workers/reference/how-workers-works/)

Cloudflare 的 Cache API 也不是一个跨所有地点统一复制的数据库：缓存数据保留在写入的数据中心，缓存操作同样局限在本地数据中心。它适合 HTTP 响应加速，不适合作为管理员刚改完价格就要求全局同步的规则正本。 [Cache API](https://developers.cloudflare.com/workers/runtime-apis/cache/)

KV 可以给读多写少的数据提供全局低延迟读取，但它仍不该取代 D1 的账本、余额和权益判定。当前规模下，把 KV 再插进来会增加一个副本、一套失效语义和更多排错路径，而没有解决“扣款必须精确”的核心问题。等到规则读量很高、又要求比 45 秒更快地跨实例传播时，再评估 KV、Durable Objects 或专门的配置发布机制更合适。

## 七、扣款正确性：缓存优化不能替代并发控制

缓存层解决的是“价格从哪里读、多久读一次”，没有解决并发扣款。两个请求同时看到余额 10、都要解锁一个 10 燃币资源时，若只是“先读余额，再插流水”，仍可能发生竞争。

正确的扣款路径需要同时满足三件事：

- 用 `(user_id, reason, ref)` 或等价幂等键保证同一资源只扣一次；
- 使用带余额条件的更新，例如 `UPDATE ... SET balance = balance - ? WHERE user_id = ? AND balance >= ?`，并检查受影响行数；
- 将成功扣款、账本记录和解锁权益放进同一组受控写入，失败时不能留下“扣了钱却没解锁”或“解锁了却没有账”的半截状态。

Cloudflare D1 支持参数绑定，避免把价格和用户 id 直接拼进 SQL；这也是构造上述条件更新的基础。 [D1 prepared statements](https://developers.cloudflare.com/d1/worker-api/prepared-statements/)

本站目前的短缓存不进入这条写路径：每一次余额读取、解锁查询和扣款判断都仍然访问 D1。随着并发增长，下一步应把条件扣减、账本与权益写入进一步收紧为可验证的原子流程，并为失败补偿和重复提交保留审计线索。缓存命中再高，也不能替代这部分约束。

## 八、运维上怎么判断这套方案够不够用

上线后不需要先假设性能数字，应直接观测以下指标。

| 指标 | 说明 | 触发下一步的信号 |
|---|---|---|
| 规则 / 资源缓存命中率 | 确认短缓存是否真的减少了 D1 读取 | 命中率低且 D1 读量高，再调 TTL 或排查 key 离散度 |
| D1 查询延迟 | 观察未命中与权益写路径的 P50 / P95 | 权益接口 P95 持续升高，优先优化 SQL 与索引 |
| 规则保存后的生效时间 | 验证用户实际看到的新价传播时间 | 超过可接受窗口，再考虑集中失效机制 |
| 解锁失败与重复请求 | 检查幂等和扣款流程 | 出现余额为负、重复扣款或账本 / 权益不一致时优先修写路径 |
| 人工调账比例 | 发现产品规则或异常入口 | 长期偏高时回看奖励、价格和风控策略 |

还应把后台展示分成两个视角。用户看到的是“这次解锁了什么、花了多少、是否永久可读”；站长看到的是规则来源、资源覆盖关系、账本流水、免费资源事件和失败原因。两套文案服务的对象不同，但都从同一份 D1 正本读取。

## 九、个人结论

对于一个以内容、工具下载和游客体验为主的站点，D1 做唯一真相源、Workers isolate 做 45～60 秒短缓存，是目前复杂度和正确性之间比较合适的平衡。

它没有承诺“每一台边缘实例立刻收到新价格”，承诺的是“价格最多短暂陈旧，用户余额和权益绝不依赖这份陈旧缓存”。把这个边界写进代码、后台说明和监控项，燃币就从一组散落的硬编码数字，变成了一套可调整、可记录、可追溯的站内权益规则。
