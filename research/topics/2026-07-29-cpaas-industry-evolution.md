CPaaS（Communications Platform as a Service，通信平台即服务）解决的是一个长期存在的工程问题：企业怎样把短信、语音、视频、即时通信等能力嵌入自己的应用，同时避开自建交换机、逐家对接运营商和维护全球通信网络的高成本。

它最早卖的是一条可调用的通信通道。今天，头部平台开始把渠道、客户数据、流程编排和 AI 放进同一套系统。行业收入仍然离不开消息量和通话分钟数，竞争焦点却已经向更高的软件层迁移。

## 一、先给结论

1. **全球 CPaaS 的商业化起点是开发者体验。** Twilio 2008 年成立，2010 年推出 SMS API，把复杂的电信网络封装成开发者熟悉的 REST API 和按量计费服务。这个模式随后被 Nexmo、Plivo 等厂商扩展。
2. **渠道数量已经很难单独构成壁垒。** 短信、语音、视频、WhatsApp、RCS 和即时通信逐渐成为标准产品。路由质量、全球合规、客户数据、工作流和交付能力决定平台能否进入更高价值的业务。
3. **中国市场经历了三次重心迁移。** 早期由容联云、云之讯等厂商聚合运营商资源；随后阿里云、腾讯云利用云生态扩大产品矩阵；2021 年以后，运营商把号码、网络、云和 AI 组合成面向政企的通信数字化产品。
4. **运营商的优势正在从“供给通道”变成“开放网络能力”。** 2023 年启动的 GSMA Open Gateway 推动号码验证、SIM 换卡、设备位置、按需网络质量等能力采用统一 API。CPaaS 厂商、云厂商和运营商因此既竞争，也互为渠道。
5. **AI 抬高了产品上限，也抬高了交付门槛。** 语音机器人、智能路由、会话摘要、质检和下一步动作可以提高单客户价值；准确率、时延、人工接管、数据授权和行业合规也随之成为成本。

## 二、CPaaS 在产业链中的位置

CPaaS 位于运营商网络和企业应用之间。它把不同国家、不同运营商、不同协议的通信资源，整理成统一 API、SDK、控制台和计费系统。

| 层级 | 主要角色 | 提供的能力 | 常见收费方式 |
|---|---|---|---|
| 网络与资源层 | 电信运营商、号码与线路提供方 | 号码、短信、语音、5G 网络、身份与位置等网络能力 | 号码租用、消息量、分钟数、网络 API 调用 |
| CPaaS 平台层 | Twilio、Vonage、容联云、云之讯、云厂商通信产品 | API、SDK、跨运营商路由、模板、编排、监控、合规工具 | 按量计费、套餐、平台订阅 |
| 应用与解决方案层 | 联络中心、CRM、营销与客服软件、行业集成商 | 客服、营销、通知、身份验证、销售管理、远程协作 | 席位费、订阅费、项目费、结果或业务量计费 |
| 企业使用层 | 互联网、零售、金融、政务、制造等组织 | 触达客户、完成服务流程、沉淀交互数据 | 以转化、效率、服务质量和风险控制衡量回报 |

基础通道具有规模经济，同时面临同质化和价格透明。平台想提高毛利，需要向上增加路由、风控、数据和软件能力；想扩大覆盖，又必须继续与底层运营商合作。这种上下游依赖决定了 CPaaS 很难成为完全脱离电信网络的纯软件生意。

## 三、全球 CPaaS 演进主线

| 阶段 | 时间 | 核心产品 | 主要客户价值 | 竞争焦点 |
|---|---|---|---|---|
| 可编程通信孕育期 | 2000—2007 | SIP、VoIP、企业通信软件 | 降低语音系统的软件化门槛 | 协议、设备兼容与线路接入 |
| CPaaS 1.0 | 2008—2014 | 语音 API、SMS API | 用代码快速加入通知和通话 | API 易用性、覆盖和价格 |
| CPaaS 2.0 | 2015—2020 | 视频、IM、隐私号码、富消息、全渠道联络 | 在多个渠道完成客户触达与互动 | 产品矩阵、全球路由、并购整合 |
| CPaaS 3.0 | 2021 至今 | AI、客户数据、流程编排、网络 API | 自动理解意图、执行流程并持续优化 | 数据闭环、行业交付、网络能力与合规 |

### 1、2000—2007：协议成熟，企业通信仍然很重

IETF 在 2002 年发布 SIP 标准 RFC 3261，为建立、修改和结束互联网多媒体会话提供了通用协议。VoIP 和软件交换技术逐渐成熟，语音从专用硬件向软件系统迁移。

企业使用通信能力仍要面对 PBX、呼叫中心设备、SIP 中继、号码资源和运营商合同。不同网络之间的接入方式、计费和监管要求并不统一。中小开发团队很难像调用支付或地图服务一样，在几天内加入电话和短信。

这一阶段完成了协议和软件基础，标准化云 API、在线自助开通和精细按量计费还没有成为主流产品形态。

### 2、2008—2014：开发者型 API 把通信变成云服务

Twilio 于 2008 年成立，目标是简化全球电信网络并把通信带到云端。公司先提供可编程语音，2010 年推出 SMS API。开发者通过 HTTPS 请求就能发送和接收消息，不再直接处理运营商协议和线路。

这个阶段的商业模式很清楚：

- 平台聚合号码和运营商通道；
- 开发者按 API 文档接入；
- 客户按消息、号码或通话分钟付费；
- 平台赚取资源采购、路由效率和服务溢价。

验证码、订单通知、预约提醒和基础呼叫成为最常见的场景。Nexmo、Plivo 等厂商沿着相近路径进入市场。CPaaS 逐渐成为描述这类服务的行业术语，但把概念归于某一家公司的单次发布并不准确。

### 3、2015—2020：从单通道 API 扩展到全渠道互动

移动互联网把客户触点拆散到 App、网页、电话、短信、社交消息和视频。企业需要统一身份、路由和会话记录，平台产品随之扩展到实时音视频、即时通信、隐私号码、WhatsApp、RCS 和云联络中心。

行业整合也在这一阶段加速。Vonage 在 2016 年收购 Nexmo，获得短信和语音 API 平台；随后又补充视频等能力。大型通信和软件企业收购 CPaaS 资产，目的是把 API 与统一通信、联络中心或企业软件组合起来。

场景从“发出一条验证码”扩大到：

- 客服在电话、网页和社交消息之间承接同一个用户；
- 房产、医疗和教育服务通过音视频远程交付；
- 出行与交易平台用隐私号码保护双方真实号码；
- 直播、游戏和社交产品用 RTC 支持实时互动；
- 营销、通知和服务消息依据用户状态自动切换渠道。

渠道扩张也带来新的成本。每个国家对号码实名、营销同意、消息模板、数据保存和跨境传输的要求不同，合规与路由运营逐渐成为平台的重要能力。

### 4、2021 至今：AI、客户数据与运营商网络 API 汇合

平台开始把会话内容转成可计算的数据。语音识别、意图判断、智能路由、自动摘要、质检、坐席辅助和对话机器人进入联络流程。大模型进一步降低了自然语言交互和流程配置的门槛。

头部厂商的产品边界也继续外扩。Twilio 当前把通信渠道、上下文数据和 AI 编排放在同一平台中；爱立信在 2022 年完成对 Vonage 的收购，希望通过 Vonage 的开发者平台开放 4G、5G 网络能力。

运营商协同开放网络能力的节点更晚。GSMA 在 2023 年发布 Open Gateway，推动运营商以统一 API 暴露号码验证、SIM 换卡、设备位置、运营商计费和按需网络质量等能力。它扩展了传统短信、语音之外的可编程通信边界。

AI 和网络 API 让 CPaaS 进入更复杂的价值区间：平台既可以理解一次对话，也可能验证号码状态、调整网络质量、触发 CRM 流程并回写业务结果。商业价值更高，跨系统集成和责任边界也更难管理。

## 四、中国 CPaaS 的本土化路径

### 1、2014—2016：初创厂商聚合运营商通道

容联云、云之讯等厂商把短信、语音、呼叫中心和音视频能力封装成 API 或 SDK，降低互联网企业接入通信能力的门槛。云之讯从 2014 年开始开展云通信业务；容联云公开资料显示，公司自 2014 年开始从事云通信业务。

市场需求高度集中在验证码、通知短信和基础语音。平台的核心工作包括采购运营商资源、管理通道路由、处理高并发、提供开发文档和完成企业资质审核。

这一模式很容易受到价格竞争影响。短信和语音的单位价格透明，客户迁移成本有限，上游资源成本又受运营商影响。只依靠通道采购价差，很难长期维持高增长和高毛利。

### 2、2017—2020：互联网云厂商扩大能力矩阵

阿里云、腾讯云把通信产品放进更完整的云服务目录。企业可以在同一个云账号中使用计算、存储、数据库、安全、AI、短信、音视频和联络中心，采购与开发路径明显缩短。

阿里云短信服务通过 API 和 SDK 提供验证码、通知等能力，当前又以 CPaaS 通信中台统一管理短信、语音和富媒体消息。腾讯云形成短信 SMS、即时通信 IM、实时音视频 TRTC、云联络中心 TCCC 等产品矩阵。

互联网云厂商的主要优势来自：

- 已有开发者账号、控制台、计费和技术支持体系；
- 通信能力可以与云计算、数据库、安全和 AI 产品组合；
- 自有互联网业务积累了音视频、即时通信和高并发经验；
- 能通过云市场和合作伙伴覆盖更多企业。

通道价格竞争在这一阶段更加激烈。厂商开始把增长方向转向实时互动、云联络中心和行业解决方案，收入单位也从“每条消息”扩展到并发、时长、席位、订阅和项目交付。

### 3、2021 至今：运营商把 CT、IT 与 AI 组合起来

中国联通在 2021 年 5 月发布联通云犀，最初定位为面向企业的一站式工作手机通信数字化方案，解决跨地区开号、缴费、发票、企业通信管理和业务流程连接等问题。

产品随后向语音 AI 和业务工作流扩展。2025 年的公开活动开始强调语音大模型；2026 年联通云犀升级为深度融合 AI 的工作流智能体平台，并发布 AI 数析、AI 助销和 AI 助手等应用。

这条路径体现了运营商的独特位置：

- **CT 资源**：号码、语音、短信、移动网络和线下服务体系；
- **IT 能力**：云资源、数据平台、软件开发和系统集成；
- **政企渠道**：省市分公司、行业客户经理和本地交付团队；
- **合规责任**：实名、反诈、营销触达和通信数据治理。

中国移动、中国电信也在推进云、5G 消息、智能客服和网络能力开放。公开资料中的产品口径并不统一，把各自的整套产品直接归为同一种 CPaaS 平台会掩盖差异。中国运营商的共同方向可以确认，具体产品范围仍需逐项核对。

## 五、三类参与者的竞争位置

| 类型 | 代表 | 主要优势 | 主要约束 | 更适合的客户与场景 |
|---|---|---|---|---|
| 独立 CPaaS 厂商 | Twilio、Vonage、容联云、云之讯 | 通信产品专注、路由运营经验、API 与行业积累 | 上游资源依赖、通道毛利承压、需要持续拓展软件层 | 多运营商接入、定制通信流程、跨区域通信 |
| 互联网云厂商 | 腾讯云、阿里云 | 开发者生态、云产品组合、音视频与 AI 技术、在线自助服务 | 通信资源仍需合作，重交付行业需要本地服务 | 互联网应用、在线业务、已有云上系统的企业 |
| 电信运营商平台 | 联通云犀及其他运营商相关产品 | 原生网络、号码与身份资源、政企渠道、本地服务和合规能力 | 跨运营商统一体验、开发者生态与产品敏捷性需要持续建设 | 政企、政务、制造、金融及本地大中型企业 |

“互联网云厂商服务线上客户、运营商服务政企客户”只能作为大体倾向。双方的客户边界正在重叠：云厂商建设政企团队，运营商发展云与开发平台，独立 CPaaS 厂商也在提供联络中心和行业方案。

更准确的竞争结构是三类能力的组合：

1. 谁能稳定取得通信与网络资源；
2. 谁能把能力做成开发者容易调用的产品；
3. 谁能进入企业流程并完成持续交付。

一家厂商很难同时在三项能力上保持绝对领先，合作与竞合会长期存在。

## 六、商业模式为什么必须上移

CPaaS 的商业模式大致经历了三层迁移。

| 商业层级 | 卖什么 | 收入单位 | 价值与风险 |
|---|---|---|---|
| 通道层 | 短信、语音、号码、流量 | 条、分钟、号码、流量 | 易理解、易规模化；同质化强、价格敏感 |
| 平台层 | API、SDK、路由、编排、监控 | 调用量、套餐、并发、订阅 | 提高开发效率和可靠性；需要持续研发与全球合规 |
| 解决方案层 | 联络中心、营销、客服、销售与行业流程 | 席位、项目、业务量、结果 | 客单价和黏性更高；销售周期、集成和交付成本也更高 |

通道不会消失。每一次消息和通话仍然要经过真实网络，基础用量也是许多平台的重要收入来源。变化发生在利润和客户关系上：平台若只负责转发，客户会持续比较单价；平台若参与身份验证、流程执行、数据回写和经营结果，替换成本和可收取的价值都会提高。

AI 延续了这条上移路径。企业购买的目标通常是减少等待、提高转化、降低人工成本或控制风险。模型调用量只是平台的成本项之一。能否把 AI 输出接入真实流程，并用完成率、人工接管率、转化率和客户满意度验收，决定了智能通信能否形成稳定收入。

## 七、全球与中国市场的结构差异

### 1、海外市场更早形成开发者型全球平台

Twilio、Nexmo 等厂商从 API 和开发者文档切入，在多国号码、消息与社交渠道上扩张。客户常常希望用一个平台覆盖多个市场，全球路由、当地监管和渠道合作因而更重要。

### 2、中国市场的运营商关系更直接

国内短信签名、模板、实名和反诈治理要求较强，通信资源与运营商体系联系紧密。平台除了提供 API，还要承担资质审核、通道治理、投诉处理和行业合规。

### 3、互联网云与运营商云形成双重平台力量

腾讯云、阿里云拥有开发者和云生态；运营商拥有网络资源、政企渠道和属地服务。独立云通信厂商位于两者之间，需要依靠产品深度、行业方案、多运营商聚合或服务效率建立位置。

这种格局很难简化为两家阵营。企业最终采购的可能是一套组合：运营商提供号码和网络，云厂商提供音视频与 AI，CPaaS 或集成商负责路由、联络中心和业务系统连接。

## 八、行业演进的四条规律

### 1、技术：单通道 API 走向智能通信平台

短信和语音 API 解决“能不能接入”；多渠道平台解决“用户从哪里来、由谁承接”；AI 和数据系统开始解决“用户想做什么、流程怎样完成、结果如何优化”。

### 2、商业：收入单位从流量走向业务价值

按条和按分钟计费仍是底座。订阅、席位、工作流、项目交付和结果计费逐渐提高收入上限。越接近业务结果，厂商承担的集成、运营和责任越多。

### 3、竞争：网络、开发平台和行业交付缺一不可

初创厂商证明了 API 模式，互联网云厂商把能力规模化，运营商把原生网络重新开放给开发者。未来的领先平台需要连接三者，单项资源很难独立完成客户互动全流程。

### 4、产品：渠道统一之后，数据闭环成为重点

全渠道的价值不只在于把短信、电话和 IM 放在一个控制台。关键是识别同一个客户、保留授权和上下文、选择合适渠道、执行下一步动作，并把结果写回 CRM、工单或经营系统。

## 九、未来 2—3 年值得观察的信号

1. **网络 API 能否跨运营商规模化。** GSMA Open Gateway 已经建立共同框架，商业覆盖、服务等级和统一结算仍决定开发者是否愿意长期采用。
2. **AI 能否改善单位经济。** 自动化带来的人工节省，需要覆盖模型、语音识别、审核、失败接管和合规成本。
3. **通道收入与软件收入能否分开增长。** 软件订阅和行业方案占比提高，通常意味着平台对单纯价格竞争的依赖下降。
4. **跨渠道身份与授权能否打通。** 用户同意、退订、号码状态、会话记录和客户身份需要在多个系统之间保持一致。
5. **运营商平台能否改善开发者体验。** 文档、沙箱、自助开通、跨省与跨运营商一致性，会影响网络优势能否变成可规模销售的产品。
6. **云厂商能否控制重交付成本。** 政企和行业客户需要本地集成、定制和持续运营，项目收入增长未必同步带来利润改善。

## 十、外部研判

CPaaS 已经进入“基础能力成熟、上层价值重新分配”的阶段。短信、语音和视频仍会增长，但它们更像云计算中的基础资源。高价值部分将集中在身份、数据、流程、AI 和行业交付。

运营商不会简单取代 CPaaS 厂商。网络 API 越丰富，企业越需要聚合、编排和统一结算；CPaaS 和云厂商可能成为运营商能力进入开发者市场的主要渠道。反过来，缺少稳定网络资源和合规运营的平台也很难只靠软件界面长期维持优势。

中国市场的胜负不会只由“CT+IT”口号决定。网络资源、开发者体验和行业交付必须同时落地。运营商在网络和政企渠道上占优，互联网云厂商在产品与开发生态上更成熟，独立厂商则需要在特定行业、跨运营商路由和服务效率上形成深度。

AI 会让通信平台更接近企业经营系统。它也会把平台从“消息是否送达”的技术责任，推向“意图是否理解、流程是否正确、决策能否审计”的业务责任。能够管理这层责任的平台，才有机会获得高于通道费的收入。

## 十一、未能验证

- 没有找到统一、可审计的公开数据，用于比较中国各类 CPaaS 厂商的通道收入、软件收入、毛利率与市场份额。
- 腾讯云、阿里云各通信产品的首次上线时间分散在不同产品线，公开页面更多展示当前能力，无法支持“某一年一次性推出完整 CPaaS”的说法。
- 中国移动、中国电信的云通信、5G 消息、智能客服和网络开放产品口径不同，尚不能将其整体收入或客户数放进同一 CPaaS 比较表。
- AI 通信产品公开案例多由厂商披露，缺少统一口径的完成率、人工接管率、转化提升和长期续费数据。
- “互联网云厂商与运营商双轮竞争”适合描述平台力量，不能覆盖独立 CPaaS、SaaS、集成商和设备商等全部参与者。
