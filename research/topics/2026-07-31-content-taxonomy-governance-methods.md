# 内容分类为何越分越乱：一次个人站返工与可持续治理方法

2026 年 7 月 31 日下午，一轮看似简单的分类调整连续暴露了六类问题：创作者经营专题被归入技术，人类成就图谱没有进入人文历史，人物内容缺少独立主题，职场筛选命中了文章却显示另一枚主题标签，主题与“技术”对象标签重复，内容类型里的“文章”也无法准确表达“精选”入口。

这些问题共享一个根因：**内容类型、讨论主题、研究对象、交付方式和编辑状态被挤进了同一组标签，数据生成、筛选和展示又各自采用不同口径。** 修改某个名称只能处理表面结果；维度没有拆开时，同类返工还会继续出现。

## 一、下午发生了什么

这轮调整的过程可以还原为一条分类故障链。

| 现象 | 原有判断 | 实际语义 | 暴露的问题 |
| --- | --- | --- | --- |
| “X 值不值得做？”进入技术类 | 标题和页面形态触发技术推断 | 创作者平台经营与内容分发 | 关键词压过内容意图 |
| “智慧边界”没有对应主题 | 数据可视化被当作主题 | 人类奖项、人物与知识成就 | 页面形态与讨论主题混用 |
| 人物内容散落在其他主题 | 只有公司、行业等对象线索 | 人物经历、思想与影响 | 人物缺少独立读者入口 |
| 选择“职场与组织”后仍显示其他主题 | 卡片固定展示首个主题 | 用户正在查看职场命中结果 | 筛选口径与展示口径分离 |
| “AI 与开发”旁又出现“技术” | 主题和研究对象同时渲染 | 两枚标签传递近似信息 | 正交维度在界面上发生冗余 |
| 内容类型显示“文章” | 底层类型 ID 为 article | 入口承担人工精选的含义 | 存储标识与展示名称绑定 |

下午完成的修正包括：

1. “X 值不值得做？”显式归入“内容创作”，并保留“商业与市场”为辅助主题。
2. “智慧边界”显式归入“人文与历史”。
3. 新增“人物观察”，人物调研拥有独立主题。
4. 多主题内容保留顺序，第一个主题作为主主题；用户按辅助主题筛选时，卡片显示当前筛选主题。
5. 主题已能表达对象含义时，隐藏重复的“技术”“人物”“公司”或“产品”对象标签。
6. 内容入口把“文章”改为“精选”，底层稳定 ID `article` 保持不变。
7. 内容源显式填写的 `subjects` 覆盖旧字段和关键词推断。

第七项最关键。系统推断适合发现候选项，无法长期承担语义正本。一个标题包含“AI”，文章可能讨论模型工程，也可能讨论创作者如何使用 AI；标题包含公司名，内容可能是公司档案，也可能是行业横向比较。最终分类需要结合内容目的与读者检索路径。

## 二、分类对象需要拆成五个维度

内容管理中常见的“分类”至少包含五种问题。

| 维度 | 回答的问题 | 规则 | 示例 |
| --- | --- | --- | --- |
| 内容类型 `contentKind` | 这是什么形式的内容 | 单选 | 分析、实践、指南、资源 |
| 内容主题 `subjects` | 它主要讨论什么 | 1–3 个，有主次顺序 | 内容创作、商业与市场 |
| 研究对象 `entityType` | 核心对象是什么 | 可选单选 | 公司、人物、产品、技术、行业 |
| 交付方式 `delivery` | 读者怎样使用 | 单选 | 阅读、交互、下载、订阅 |
| 固定系列 `series` | 是否属于持续栏目 | 可选单选 | 前端周看、月度回顾 |

“精选”“热门”“最新”更适合放在编辑状态或排序策略中。它们会随运营判断和时间变化，不应改变内容的主题归属。当前界面使用“精选”作为 `article` 入口的展示名称，解决了读者侧的表达问题；如果未来该入口严格表示人工策展，还需要把策展状态单独建模，避免 `article` 同时承担文体和推荐状态。

[Dublin Core Metadata Terms](https://www.dublincore.org/specifications/dublin-core/dcmi-terms/) 分别定义了 `subject` 与 `type`：前者描述资源的主题，后者描述资源的性质或体裁。这个分离原则对个人站同样有效。技术文章可以采用“指南”形式，公司调研可以采用“档案”形式；形式不能替代主题。

## 三、主题表需要成为受控词表

主题管理的基本单位应该是概念记录，而非一段可随手修改的中文文本。每个主题至少需要这些字段：

| 字段 | 用途 | 示例 |
| --- | --- | --- |
| 稳定 ID | 代码、URL、数据统计长期引用 | `content_creation` |
| 首选名称 | 当前界面展示 | 内容创作 |
| 别名 | 搜索、迁移和旧称兼容 | 创作、内容与媒体 |
| 定义 | 说明概念覆盖范围 | 写作、媒体、分发与创作者经营 |
| 纳入 | 提供典型正例 | 平台经营、写作方法、视觉生产 |
| 排除 | 处理相邻主题边界 | 一般职场沟通、纯底层开发 |
| 状态 | 控制启用、合并或停用 | active |
| 关系 | 表达上位、下位或相关概念 | broader / narrower / related |

[W3C 的 SKOS 规范](https://www.w3.org/TR/skos-reference/) 为这类知识组织系统提供了通用模型：概念拥有 `prefLabel`、`altLabel`、`definition` 等属性，也能通过 `broader`、`narrower` 和 `related` 表达关系。个人站无需完整实现 RDF，也可以复用它的设计原则：**概念身份与展示文字分离，别名与首选名称分离，层级关系与相关关系分离。**

[ANSI/NISO Z39.19-2005 (R2010)](https://www.niso.org/publications/ansiniso-z3919-2005-r2010) 把受控词表的内容、展示、构建、测试、维护和管理放在同一套规范中。分类表因此不只是前端筛选配置；它需要定义、测试样本、变更记录和维护责任。

## 四、显式标注优先，推断进入治理队列

可行的分类流水线分成三层。

### 1. 内容源保存人工判断

每条内容在 frontmatter 或内容注册表中保存 1–3 个 `subjects`。顺序表达主次，稳定 ID 负责跨版本引用。

~~~yaml
subjects: [content_creation, business_market]
~~~

主主题决定默认卡片标签，辅助主题负责扩展发现路径。多主题数量需要限制；标签过多会降低每个标签的区分度，也会让统计失真。

### 2. 旧字段与关键词只提供回退

存量内容没有显式主题时，可以根据目录、旧分类、资源类型和关键词生成候选结果。候选结果必须标记来源，例如“系统推断”，并进入后台待治理列表。

推断规则适合完成两件事：保证旧内容暂时可浏览，帮助维护者缩小人工复核范围。它不适合静默覆盖已经确认的主题。

### 3. 筛选与展示共享上下文

一条内容拥有多个主题时，默认列表展示主主题；用户选择辅助主题后，卡片展示该辅助主题。筛选结果与视觉反馈因此保持一致。

对象标签还需要去重规则。当“人物观察”已经出现时，“人物”对象标签提供的信息很少；当主题为“AI 与开发”时，再显示“技术”也容易形成噪音。对象字段仍然可以保留在数据层，用于查询、推荐和后续分析。

## 五、后台分类管理应该管理什么

第一版分类后台包含四块能力：

1. **受控词表**：查看稳定 ID、首选名称、别名、定义、纳入与排除边界。
2. **分布审计**：统计各主题的主主题数量和全部命中数量，发现过密、过疏或边界重叠。
3. **来源审计**：区分人工显式分类与系统推断，形成可逐条处理的迁移队列。
4. **治理规则**：记录改名、新增、合并、停用、抽样和验证流程。

第一版不提供直接修改 Markdown 的网页表单。调研文件和内容注册表仍是分类正本，后台负责观察、检索和决策。等编辑 API、权限校验、版本记录和回滚能力齐备后，再加入写入操作。这样可以避免界面显示“保存成功”，实际构建数据却没有变化的双重来源。

## 六、持续演进需要哪些指标

分类质量无法用主题数量衡量。更有用的指标包括：

| 指标 | 计算方式 | 说明 |
| --- | --- | --- |
| 显式分类覆盖率 | 有 `subjects` 的内容 / 全部内容 | 反映人工治理进度 |
| 推断依赖量 | 仍使用旧字段推断的内容数 | 形成待办队列 |
| 多主题率 | 拥有 2–3 个主题的内容 / 全部内容 | 过高时可能边界太宽 |
| 主次倒置样本 | 辅助主题比主主题更符合标题和摘要的数量 | 检查排序质量 |
| 稀疏主题 | 长期内容量低于约定阈值的主题 | 判断是否合并或停止扩展 |
| 重复标签率 | 同一卡片出现语义重复标签的比例 | 检查界面噪音 |
| 零结果筛选 | 用户选择后没有结果的次数 | 判断导航是否制造空入口 |

新增主题前需要准备定义、相邻主题差异、至少若干正例和反例，以及未来内容来源。主题改名只改变首选名称，稳定 ID 与历史统计继续保留。主题合并时保留旧 ID 的映射和变更说明，避免旧链接与分析数据失效。

一次迭代可以按以下顺序完成：收集错分案例，修改边界定义，抽查正例与反例，更新显式主题，运行分类测试，构建预览，最后观察筛选和搜索数据。每次只处理一组边界，问题更容易定位。

## 七、结论

今天下午花费较多时间，直接原因是逐个修正错分和显示问题；更深层的原因是分类体系缺少统一正本、维度边界和治理入口。

这轮返工已经形成一套可延续的方法：

- 内容类型、主题、对象、交付方式和系列分别建模；
- 主题使用稳定 ID、首选名称、别名、定义与边界；
- 人工显式主题覆盖系统推断；
- 多主题保存主次顺序，筛选与卡片显示共享上下文；
- 后台持续显示主题分布、推断队列和治理规则；
- 改名、新增与合并都经过样本检查、测试和构建验证。

分类工作的目标是缩短读者从问题到内容的路径，也让后续新增内容能够复用同一套判断。分类表开始承担定义、审计和演进职责后，下一次错分会成为可追踪的治理任务，而不会继续变成一轮散落在代码和页面里的返工。
