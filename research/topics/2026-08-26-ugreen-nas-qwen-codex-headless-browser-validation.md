先说结论：我在绿联 DXP4800 Plus 上完成了“调用 Qwen → 启动 Codex → 无头浏览器打开百度并点击按钮”的一次性验证。整条运行链当时都在 NAS 内执行，没有依赖 Mac。

但这件事还没有完全闭环。最后补写的浏览器控制服务和编排脚本仍停留在本地工作目录，没有上传到 NAS，也没有用更新后的 Compose 重建 UGOS 项目。浏览器控制端点能否在容器重启后自动恢复，目前没有经过实测。

所以，准确状态是：**功能链路已经跑通一次，持久化重启验证还没做完。** 我上一条用“已经执行完成”概括整个任务，口径过满，这里一并更正。

## 一、最开始想完成什么

目标很具体，一共六项：

1. 所有组件都运行在绿联 DXP4800 Plus 上；
2. 使用 NAS 上的 `qwen3.5:9b`，不调用 OpenAI API；
3. Codex CLI 运行在 NAS 内；
4. Chromium 以无界面方式运行在 NAS 内；
5. 输入一条提示语后，系统依次调用 Qwen、Codex 和浏览器，最后打开网页并点击按钮；
6. 容器重启后，整套服务可以自动恢复。

前五项完成了一次运行验证。第六项还缺部署和重启复测。

## 二、NAS 上实际运行了哪些组件

这次验证使用三个容器角色。

| 组件 | 作用 | 验证状态 |
|---|---|---|
| `ollama` | 运行本地模型 `qwen3.5:9b` | 已运行 |
| `ugreen-codex` | 安装并运行 Codex CLI | 已验证使用 NAS Ollama |
| `ugreen-browser-agent` | 运行 Playwright 和无头 Chromium | 已打开百度并完成点击 |

Codex 的模型地址指向 NAS 上的 Ollama OpenAI 兼容接口：

```text
http://<NAS_LAN_IP>:11434/v1
```

我还修正了 Codex 使用的本地模型元数据，避免它错误套用 OpenAI 模型信息。最终日志明确显示：

```text
model: qwen3.5:9b
provider: ollama
```

这两行很关键。只看到 Codex 命令成功启动，无法证明它实际用了哪个模型和 provider。

Chromium 还遇到用户目录权限问题。容器内原先使用的 profile 路径不可写，浏览器无法正常启动。我把 profile 改到：

```text
/tmp/browser-profile
```

这个修改解决了当次运行，但 `/tmp` 本身是临时目录。容器重建后 profile 消失可以接受，控制服务能否自动重新启动才是持久化验证真正要检查的部分。

## 三、理想路径在三个兼容点上卡住了

我最初选择的路径是：

```text
Qwen
  → Codex 原生工具调用
    → Playwright MCP
      → Chromium
```

结构很漂亮，实际组合却不稳定。

第一个问题发生在 Qwen 与 Codex 工具调用之间。`qwen3.5:9b` 通过 Codex 调用 MCP 工具时，工具名称和参数格式的兼容性会波动。有时模型能识别浏览器工具，有时生成的调用形状无法被 Codex 正确执行。

第二个问题发生在 Playwright MCP 的 HTTP 多步骤会话。导航、输入、点击需要共享同一个浏览器上下文，但连接和会话会在步骤之间丢失。单个动作偶尔能成功，连起来后很难稳定复现。

第三个问题来自我自己的权限配置。为了限制 Codex，我曾设置：

```ini
enabled_tools = [
  "browser_navigate",
  "browser_snapshot",
  "browser_type",
  "browser_click",
  "browser_wait_for"
]
```

这份白名单把 Shell 工具一起隐藏了。Qwen 随后明确报告没有 `shell_command`，后续验证自然无法执行。问题出在工具白名单，与 NAS 性能和 Qwen 能力无关。

如果重新做一次，我会先保留最小可用的 Shell 能力，用确定性脚本把端到端链路跑通，再逐项收紧权限。权限收口仍然必要，顺序应该放在基线验证之后。

## 四、最终跑通的是一个确定性浏览器端点

继续消耗时间调 MCP 会话的收益已经很低。我临时在 `ugreen-browser-agent` 容器里启动了一个 Playwright HTTP 控制端点，监听 `8935` 端口。

这个端点只做一件固定的事：

1. 启动无头 Chromium；
2. 打开百度；
3. 在搜索框输入 `NAS Qwen 浏览器验证`；
4. 点击“百度一下”；
5. 返回点击后的页面标题和 URL。

最终的 NAS 内编排命令依次完成三项检查：

```text
直接调用 Qwen
  → 启动 Codex，并指定 qwen3.5:9b
    → 请求 browser-agent:8935
      → 打开百度、输入文字并点击按钮
```

日志返回：

```json
{
  "qwen": "QWEN_OK",
  "codex": "CODEX_OK",
  "browser": {
    "ok": true,
    "title": "百度安全验证",
    "url": "https://wappass.baidu.com/..."
  }
}
```

页面进入“百度安全验证”，说明表单提交已经发生，百度随后触发了反自动化验证。它证明点击和跳转执行成功，也同时说明这套脚本不能把“得到正常搜索结果页”当成稳定验收条件。

更合适的浏览器验收标准应该是：输入框出现指定文本、点击动作成功触发、页面 URL 或标题发生预期变化。需要稳定测试 DOM 操作时，应换成自己控制的测试页，避免把第三方反爬策略混进功能验收。

## 五、时间主要花在哪里

这次任务慢，原因可以归到四类。

### 1. 在不稳定路径上停留太久

Qwen 9B、Codex 自定义 Ollama provider、Playwright MCP HTTP 会话同时加入后，排障变量太多。我连续测试原生 MCP 工具调用，直到后面才换成确定性 HTTP 编排。

更省时间的顺序是逐层建立基线：

```text
Chromium 脚本可运行
  → HTTP 控制端点可调用
    → Codex 可调用端点
      → Qwen 和 Codex 串联
        → 最后再尝试 MCP 化
```

每加一层只引入一个新变量，失败时更容易知道问题在哪。

### 2. 工具白名单提前收得太紧

工具权限配置错误直接切断了后续 Shell 验证。这个问题表面上像模型不会调用工具，实际检查 Codex 可见工具列表就能发现。

经验很简单：先验证模型看到了哪些工具，再分析模型为什么没有调用。工具根本不可见时，继续改提示词没有意义。

### 3. 失败进程没有及时清理

我用后台方式启动过多次 `codex exec`。其中几个进程一直等待 Ollama 推理，占住了本地模型队列。新任务看起来像“NAS 很慢”或“模型没有响应”，实际是在等前面的遗留任务。

清理遗留 Codex 进程后，最终验证很快就完成了。后续至少要加三条运行纪律：

- 每一轮设置明确超时；
- 失败后立即结束对应进程；
- 开始下一轮前检查 Codex 进程和 Ollama 队列。

本地模型的并发能力有限。后台任务没有退出时，重复点击执行只会继续积压。

### 4. UGOS 网页终端放大了每次试错成本

整个部署通过 UGOS 网页里的 Docker 终端完成。一次点击、输入或截图经常需要约 30～60 秒，会话还多次超时重置。

每次重连都要重复打开 UGOS、进入 Docker、找到容器、打开终端、新建 Shell、查看日志。单个动作不复杂，累积等待占了总耗时的大头。

如果 NAS 开启 SSH，同样的文件上传、容器重建、日志查看和进程清理可以直接在终端完成，排障时间会明显缩短。SSH 也更适合保存命令记录，减少网页终端里复制失败或漏输参数的情况。

## 六、为什么现在还不能写“完全完成”

当次成功依赖的是容器内临时启动的 `8935` 控制端点。验证完成后，我又在工作电脑上生成了三个持久化部署产物：

- `browser-control.mjs`；
- `nas-agent.mjs`；
- 更新后的 `compose.ugos-ui.yaml`。

JavaScript 和 YAML 语法已经检查过，但这些文件没有上传到 NAS 的 `/volume1/docker/ugreen-browser-agent`，UGOS 项目也没有使用新 Compose 重建。

这会造成一个很容易误判的状态：代码文件看起来已经准备好，当时的功能也确实成功过，NAS 上的实际部署状态却没有包含这些新增内容。只要容器重启，临时启动的浏览器控制端点就可能消失。

当前状态应按部署事实记录：

| 项目 | 状态 |
|---|---|
| NAS Ollama + `qwen3.5:9b` | 已运行 |
| Codex 使用 NAS Ollama | 已验证 |
| 无头 Chromium | 已运行 |
| 打开百度并点击按钮 | 已验证 |
| 单命令依次调用 Qwen、Codex、浏览器 | 已验证 |
| 当次运行不依赖 Mac | 已验证 |
| 浏览器控制端点随容器自动恢复 | 尚未验证 |
| 持久化 Compose 实际部署到 NAS | 尚未完成 |

## 七、最后四步才是真正的闭环

剩余工作已经收敛到四步。

第一步，把 `browser-control.mjs` 和 `nas-agent.mjs` 上传到 NAS 的浏览器 Agent 项目目录。

第二步，用更新后的 `compose.ugos-ui.yaml` 重建 `ugreen-browser-agent` 项目，确认控制服务由容器启动命令或受管进程自动拉起。

第三步，在 NAS 内运行：

```bash
node /install/nas-agent.mjs "NAS Qwen 浏览器验证"
```

验收结果至少应同时满足：

```text
Qwen 有响应
Codex 返回 CODEX_OK
browser.ok = true
```

第四步，主动重启相关容器，再运行一次相同命令。只有这次复测仍然成功，才能确认服务自动恢复、运行链不依赖工作电脑、持久化配置与实际部署一致。

最好再多加一项：记录容器启动时间、控制端点健康检查和此次运行使用的 Compose 文件哈希。这样以后看到一次成功日志时，可以知道它来自临时进程还是持久化版本。

## 八、这次最值得留下的经验

这次排障让我重新确认了几条很朴素的工程习惯。

**先跑最短闭环。** 浏览器、HTTP 端点、Codex、Qwen 逐层接入。每一层都有独立可观察的输入和输出。

**先看工具是否存在。** 模型没有调用某个工具时，先查工具清单、权限和 schema，再改提示词。

**本地模型要管理队列。** 每轮任务有超时、有清理，重试前确认旧进程已经退出。

**部署完成要以运行环境为准。** 本地文件写好、语法检查通过，只能说明部署材料准备好了。文件进入 NAS、Compose 完成重建、容器重启后复测成功，才构成可恢复的交付。

**第三方网站适合演示，不适合做唯一验收页。** 百度安全验证证明提交发生过，也暴露了第三方反自动化策略会干扰结果。长期回归测试应使用可控页面。

这次已经证明 DXP4800 Plus 能在 NAS 内承载 Ollama、Qwen、Codex 和无头 Chromium，并完成一次顺序编排。剩下的工作量不大，但它决定了这套方案是一段成功日志，还是一项容器重启后仍然可用的能力。
