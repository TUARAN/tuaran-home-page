## 一、核心结论

1. **记忆需要一条完整的数据处理链。** 完整链路包括：记录事件、识别值得保留的信息、提取、分类、核验、去重、处理冲突、持久化、检索、注入、纠正和删除。
2. **会话继续、上下文压缩、长期记忆、用户画像是四件不同的事。** 能恢复昨天的聊天，不代表能在新任务里正确使用昨天学到的偏好。
3. **成熟方案通常把规则与经验分开。** 人工制定的规则应稳定、可审查；模型提取的经验应带来源、作用范围与不确定性，不能自行升级成权限。
4. **自动更新有多种触发方式。** 工作过程中主动记笔记、每轮后台观察、会话空闲后提取、每晚汇总、压缩时整理，各有不同的成本和错误风险。
5. **不要把全部历史塞入每次请求。** 更可控的组合是“简短常驻信息 + 当前任务状态 + 按需检索 + 可回溯证据”。
6. **本地保存不等于本地推理，也不等于从不出网。** 磁盘上的记忆被注入云端模型请求时，其内容仍会发送给模型服务。
7. **跨工具共享的重点是统一语义、身份、权限和删除机制。** 直接把五款工具的记忆目录双向同步，容易造成冲突、隐私串用和错误放大。
8. **衡量记忆价值，应看它是否减少重复纠正、提高任务成功率。** 记住多少条、画像有多长、向量数量有多大，都不是目标。

推荐架构属于设计建议，产品机制与公开证据在各节分别标注。

## 二、先建立正确的分类方式

### 2.1 按内容与用途分

| 类型 | 解决什么问题 | 应保存什么 | 不应混入什么 |
|---|---|---|---|
| 当前上下文／工作记忆 | 这一步正在做什么 | 当前目标、约束、最近消息、正在使用的工具结果 | 无关项目的全部历史 |
| 会话持久化 | 退出后如何继续 | 消息、工具调用、任务状态、检查点 | 未经核验的永久画像 |
| 情景记忆 | 过去发生过什么 | 某次任务的经过、决策、结果、时间和证据 | 把一次经历概括成永远有效的规则 |
| 事实与语义记忆 | 哪些知识以后仍有用 | 项目约定、已确认事实、已验证的操作条件 | 可以廉价从当前代码重新确认的重复副本 |
| 用户画像与偏好 | 如何更适合这个人 | 用户明确的语言、格式、协作偏好及适用场景 | 从单次提问推断职业、身份或敏感特征 |
| 程序性记忆 | 下次如何更好地完成 | SOP、Skills、排错流程、验证步骤、停止条件 | 只有成功宣言、没有操作证据的“经验” |
| 项目与任务状态 | 当前进度在哪里 | 待办、阻塞、已完成项、环境版本、交付物位置 | 长期不清理的临时状态 |
| 外部知识库 | 参考资料在哪里 | 文档、邮件、手册、代码、来源索引及访问权限 | 自动视为用户立场或行为指令 |
| 审计记录 | 为什么记住、使用或删除 | 来源、版本、审批、读写与删除记录 | 被当作每轮都要注入的背景全文 |

LangGraph 明确区分 thread 内的状态持久化与跨 thread 的长期 Store；它的记忆概念也区分事实、经历与操作方法。可以借鉴这种分类，但不必照搬其技术栈。[LangGraph 记忆概念](https://docs.langchain.com/oss/python/concepts/memory)、[持久化与 Store](https://docs.langchain.com/oss/python/langgraph/persistence)

**另外两种常被误叫成“记忆”的东西：**

- **Prompt cache／KV cache**：缓存已计算的上下文以节省推理成本，不自动产生用户画像或新的事实库。Claude Code 的提示缓存发生在模型服务侧，且会受前缀变化与有效期影响。[Claude Code Prompt caching](https://code.claude.com/docs/en/prompt-caching)
- **模型参数里的知识**：训练得到的知识不是本次会话写入的文件。常规 agent memory 通过外部状态和上下文工作，不等于每轮给模型做微调。

### 2.2 按正交维度管理，而不是只有一棵目录树

一条记忆至少需要回答六个问题：

| 维度 | 示例 |
|---|---|
| 内容类型 | 偏好、事实、决策、经历、流程 |
| 作用范围 | 本轮、本任务、本项目、某位用户、某个团队 |
| 存储位置 | 本地文件、本地数据库、自托管服务、厂商云 |
| 可信状态 | 待核验、用户确认、工具验证、已过期、已撤销 |
| 时间范围 | 当时有效、目前有效、到某日失效 |
| 使用权限 | 可读取、可提取、可注入、可同步、可分享 |

例如，“本项目使用 pnpm”可以是已验证的项目事实，不能自动变成“用户在所有项目都偏好 pnpm”。“这次请详细解释”是任务要求，也不能自动覆盖用户平时偏好简洁的习惯。

### 2.3 “分级”需要分别管理权威性与可信度

- **权威性**决定某条内容有没有资格约束行为：权限与安全政策应由产品机制执行；当前任务指令与明确规则按产品指令层级处理。检索到的笔记不能自行扩大权限。
- **可信度**决定事实是否值得采用：用户明确陈述、当前工具核验、带来源的历史记录、模型推断，应区分标记。
- **适用范围**先于简单排序：即使很可信，项目 A 的事实也不应自动用于项目 B。
- **新旧关系**不是绝对优先级：新导入的旧材料不应覆盖最近验证的现状；当前明确要求可以暂时覆盖默认偏好，而不必永久改写画像。

因此，不推荐用一个“重要性分数”同时承担权限、可信度、相关性和时效判断。先做硬性过滤，再做相关性排序更清晰。

## 三、五款产品的横向比较

下表是定位概括，具体事实与边界见后续产品小节。

| 产品 | 可确认的核心路线 | 自动更新方式 | 画像定位 | 本地／云端边界 |
|---|---|---|---|---|
| Claude Code | 人工规则 + 项目自动笔记 + 按需主题文件 | agent 工作过程中选择保存 | 偏好与反馈纳入项目记忆 | 自动笔记是机器本地状态；不默认跨机器共享 |
| Codex | 规则 + 会话提取 + 全局整理 + 渐进检索 | 后台分阶段处理符合条件的历史 | 从用户纠正、约束和偏好提炼 | 本地记忆库与 ChatGPT 记忆分开 |
| Hermes Agent | 有限核心记忆 + 独立用户档案 + 历史全文搜索 | 主动写入、回合后复盘，可设审批 | 有明确的 USER.md；可扩展用户建模 | 内置存储本地；外部 provider 可云端或自托管 |
| Cursor | 当前规则系统 + 云端自动化持久笔记；历史上有 Chat Memories | 自动化运行中读写；历史 Memories 有后台生成审批 | 当前个人通用画像机制未充分确认 | 自动化笔记在工作文件系统之外持久化 |
| WorkBuddy 桌面端 | 从历史提取个人记忆 + 相关背景注入 + 会话检索 | 官方明确为每晚整理 | 直接覆盖偏好、关系及跟进事项 | 官方该页未交代具体数据库位置与跨设备一致性 |
| CodeBuddy Code（补充） | 分层规则 + Typed Auto Memory | 会话内自动记忆与可选后台提取分别配置 | 类型化条目，个人／项目／团队范围 | 有明确的个人与团队目录布局 |

### 3.1 Claude Code：项目笔记与规则分离

官方把人工 `CLAUDE.md` 与 Auto Memory 分开。自动记忆默认开启，条目有 user、feedback、project、reference 四类；项目笔记位于 `~/.claude/projects/<project>/memory/`。启动先加载 `MEMORY.md` 的前 200 行或 25KB，以先到者为准，主题文件按需读。同仓库 worktree 共用，但不自动跨机器共享。不是每个会话都必定保存。[官方 Memory 文档](https://code.claude.com/docs/en/memory)

会话本身另以 JSONL 持久化，支持恢复、分叉与导出。上下文压缩后，启动规则与自动记忆会重新注入，部分按路径触发的规则需要再次遇到相关文件才加载。[会话管理](https://code.claude.com/docs/en/sessions)、[上下文窗口](https://code.claude.com/docs/en/context-window)

**设计启发：** 短索引负责发现，原始资料负责核验；“你告诉我怎样协作”与“我从任务中学到什么”应分开管理。建议把项目笔记当作带证据的辅助材料，重要安全边界交给权限与可执行控制。

### 3.2 Codex：提取与整理分成两个阶段

官方本地记忆默认关闭，可分别控制使用已有记忆和让会话成为未来提取输入。记忆位于 Codex home 下的 `memories/`，与 ChatGPT 的记忆系统分开；后台不会在每次聊天结束时立即更新。[官方 Memories 文档](https://learn.chatgpt.com/docs/customization/memories)

公开源码描述了两个阶段：

1. **逐会话提取**：筛选满足来源、空闲时间和扫描预算等条件的历史；生成原始记忆与会话摘要，并做秘密信息脱敏。
2. **全局整理**：获取单写锁，挑选候选输入，更新本地材料，再由整理过程合并经验。候选选择考虑使用记录与时间窗口，不只是“最近聊过什么”。无变化时可以跳过整理。[官方源码：Memories pipeline](https://github.com/openai/codex/blob/main/codex-rs/memories/README.md)

读取层先提供 `memory_summary.md`，再搜索 `MEMORY.md`，必要时读取会话摘要、流程及原始证据。提取模板强调：用户消息是偏好证据，工具结果是执行事实证据；助手自述不能代替成功验证。[读取模板](https://github.com/openai/codex/blob/main/codex-rs/ext/memories/templates/memories/read_path.md)、[提取模板](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/stage_one_system.md)

**设计启发：** 写入需要有调度、去重、锁、失败重试和增量处理；“整理器”不应与前台回答无边界地争抢资源。读取频繁可以作为重要性信号，但不能单独证明某条记忆正确。

### 3.3 Hermes Agent：核心记忆、用户档案、历史检索分开

Hermes 的内置 `MEMORY.md` 与 `USER.md` 分别保存工作知识与用户档案，默认字符预算不同；会话开始时以冻结快照加载。agent 可增删改条目，并可在回合后复盘。`write_approval` 可让写入先审批；关闭通知不等于关闭写入。SQLite/FTS5 支持查找历史会话。[Persistent Memory](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory/)

提示构建又区分较稳定的身份／规则、项目上下文和变化较快的记忆层，以兼顾缓存与当前相关性。其压缩方案保留摘要、精确标识符以及恢复历史的入口，减少摘要改写文件路径或错误信息造成的损失。[Prompt Assembly](https://hermes-agent.nousresearch.com/docs/developer-guide/prompt-assembly/)、[Compression and Caching](https://hermes-agent.nousresearch.com/docs/developer-guide/context-compression-and-caching/)

可选外部 memory provider 能在每轮前预取、响应后同步、会话结束时提取，并提供额外检索工具。Honcho 集成进一步支持用户与 AI peer 的不同观察视角。因此，开启 provider 不只是“备份两个 Markdown”，可能改变会话数据流向。[Memory Providers](https://hermes-agent.nousresearch.com/docs/user-guide/features/memory-providers/)

**设计启发：** 小而稳定的核心信息适合常驻，庞大历史适合检索。用户档案的自动写入应该独立可控；多角色助手可以共享已确认事实，却不必共享所有推断。

### 3.4 Cursor：务必区分历史 Memories 与当前 Automations

Cursor 2025 年发布记录确认过项目内个人 Memories，并在 1.2 中加入后台生成内容的用户审批。旧文档描述过旁路模型观察对话；但该文档入口在此次访问时已跳到文档首页，因此不把旧实现直接当作 2026 年所有客户端的现状。[1.0 发布记录](https://cursor.com/changelog/1-0)、[1.2 发布记录](https://cursor.com/changelog/1-2)

当前规则文档支持全局、团队、项目与 `AGENTS.md`，并可按始终加载、文件匹配、相关性判断或手动引用应用。这是一种可控的上下文路由，不应等同于自动画像。[Rules](https://prod.cursor.com/docs/rules)

当前云端 Automations 文档明确：同一自动化的多次运行可以共享持久笔记，默认入口名为 `MEMORIES.md`，存于 agent 工作文件系统之外，支持查看、编辑、删除及关闭；官方同时警告不可信输入会污染后续运行。[Automations — Memories](https://cursor.com/docs/cloud-agent/automations#memories)

**设计启发：** 定时任务应拥有独立运行记忆，例如上次处理位置与已通知事件。不要让自动化任务把未经审查的外部内容变成全局规则。

### 3.5 WorkBuddy：明确的每日个人记忆提取

WorkBuddy 桌面端官方说明：记忆默认开启，每晚从当日会话提炼事实、偏好、人物关系及跟进事项；后续按相关性注入背景，也支持历史检索。用户能查看、更正、删除、关闭，并通过粘贴其他 AI 的总结导入记忆。文档称提取不额外消耗用户积分、仅供本人使用，但没有公布提取提示词、具体存储后端或检索排序算法。[WorkBuddy 官方记忆说明](https://www.codebuddy.cn/docs/workbuddy/From-Beginner-to-Expert-Guide/Function-Description/Memory)

**不能据此断言：** 全部记忆都在本地 Markdown、导入就是实时同步、关闭提取等于删除历史、删除会撤回已生成的输出，或“仅本人可见”等于模型处理完全不出网。

**设计启发：** 面向办公助手，用户关系、进行中的事项和输出偏好可能比代码索引更有用；但关系信息与第三方个人信息需要更谨慎的来源和共享控制。

### 3.6 CodeBuddy Code：不要与 WorkBuddy 桌面记忆混为一谈

CodeBuddy Code 官方设置列出：Auto Memory、Typed Memory 和相关性选择默认开启；后台会话提取 `memoryExtraction` 默认关闭。类型包含 user/feedback/project/reference，相关性注入最多选择 5 条；个人、全局和团队记忆有不同目录。[官方 CLI 设置](https://www.workbuddy.ai/docs/cli/settings)

其规则又分用户、项目、模块和本地项目偏好，支持 `CODEBUDDY.md`、`CODEBUDDY.local.md` 与规则目录。这是规则组织层，不等于上述后台提取开关。[腾讯云官方：记忆](https://cloud.tencent.cn/document/product/1831/137011)

**设计启发：** “自动记忆已开启”可能只开启某个写入路径；必须分别检查保存、后台提取、检索使用和团队共享，不能只看一个总开关。

## 四、自动化提取：何时写，比“能不能写”更重要

### 4.1 五种常规触发方式

| 方式 | 优点 | 风险与成本 | 适用场景 |
|---|---|---|---|
| 用户明确说“记住／忘记” | 意图清晰，易确认 | 容易漏掉隐含经验；仍要识别范围 | 稳定偏好、重要约定 |
| 前台 agent 工作中决定保存 | 有完整任务上下文 | 增加主链路耗时，可能把计划当事实 | 明确纠正、已验证结果 |
| 每轮旁路观察 | 捕捉及时，前台负担小 | 重复提取多、成本高、尚未完成的任务易误判 | 长期助理，强时效需求 |
| 会话空闲／结束后提取 | 能看完整过程与结局 | 更新延迟；“结束”事件可能不可靠 | 编码任务、调研报告 |
| 每晚／定期整合 | 容易跨任务去重与归纳 | 当天的新偏好未必立即可用 | 办公画像、工作复盘 |

Claude Code 的会话中笔记、Codex 的后台两阶段流程、Hermes 的回合后复盘和 WorkBuddy 的夜间提取，分别体现不同取舍。表中的取舍分析属于设计判断，不代表产品性能测试。

### 4.2 推荐采用“快速更新 + 延后整合”

**快速通道：** 明确的记住／忘记、用户纠正、已验证的状态变化，形成结构化候选；对于撤销和禁止使用，应尽快阻断旧记忆的后续检索。

**延后通道：** 等任务有结果或会话空闲，再总结经验。定期合并重复条目、检查矛盾、刷新索引和过期状态。

**压缩前：** 保存仍在推进的目标、验收标准、文件／工单标识、最近验证结果和未决问题。它首先是“工作交接”，不应自动把所有内容写成长期画像。

**防崩溃：** 不只依赖正常退出 hook。使用增量游标与周期性检查，让异常退出之后仍能处理尚未提取的部分。每次处理记录源事件范围，避免重启后重复写入。

### 4.3 提取对象与证据等级

| 输入 | 应如何对待 | 示例 |
|---|---|---|
| 用户明确偏好或纠正 | 强偏好证据，仍须限定范围 | “这类周报先列结论” |
| 工具验证的事实 | 强执行证据，记录环境版本 | 测试命令与实际结果 |
| 用户批准的方案 | 可保存为决策 | “这个项目选择方案 B” |
| 助手的计划／承诺 | 只能保存为待办，不算完成 | “我会帮你部署” |
| 助手推断 | 候选，不能直接变成确知画像 | “用户可能更喜欢表格” |
| 网页、邮件、引用文字 | 带来源的资料，不是用户意图 | 客户邮件里提出的要求 |
| 工具失败和临时噪声 | 只保留可复现且有教训的部分 | 一次偶发超时通常不入长期库 |

Codex 的提取模板明确强调区分用户证据、工具证据和助手叙述，并允许没有高价值信息时不生成记忆。这是值得沿用的最低门槛。[Stage-one extraction template](https://github.com/openai/codex/blob/main/codex-rs/memories/write/templates/memories/stage_one_system.md)

## 五、推荐的完整生命周期

以下是**可实施的通用设计**，不是某一个产品的内部架构。

```text
经授权的会话、工具结果、文件事件
                ↓
限定采集范围 → 敏感内容过滤 → 事件去重
                ↓
提取原子候选：事实 / 偏好 / 状态 / 经验 / 流程
                ↓
核对来源、主体、时间、项目、完成状态
                ↓
与已有记录比较：新增 / 补充 / 替代 / 冲突 / 忽略
                ↓
策略审核：自动接受 / 人工确认 / 拒绝
                ↓
事实记录与版本历史 → 当前有效视图 → 检索索引
                ↓
权限过滤 → 相关检索 → 重排 → 预算裁剪 → 注入
                ↓
使用效果、用户纠正、到期检查 → 更新或撤销
```

### 5.1 原子化，但不要丢掉解释

不好的记录：“用户喜欢中文、经常写代码、周报要短、上次数据库坏了，可能准备换工具。”

更好的记录：

- 默认交流语言：中文；来源是明确要求；用户范围。
- 周报先给结论；只适用于周报；来源是修改反馈。
- 某项目数据库连接失败；截至某时间未修复；任务状态。
- 工具更换仅是讨论；不得记为已决定。

每条记录可以很短，但应保留“何时适用、为什么存在、哪里能核验”。

### 5.2 更新有两条路线

**路线 A：维护当前事实。** 新信息到来后更新条目，同时保留版本历史。读取简单，适合小型个人记忆。

**路线 B：追加事件，计算当前状态。** 历史事实不被静默覆盖，通过有效时间、替代关系和查询语境判定“现在是什么”。审计与时间推理更强，但检索和删除更复杂。

Mem0 的新算法文档显示其由提取时增改删转向单次 ADD-only 提取，用时间语境与混合检索处理历史变化。这说明“记忆优化”不一定等于反复覆盖文件；但 ADD-only 提取不意味着系统可以忽略用户删除请求。[Mem0 新算法迁移说明](https://docs.mem0.ai/migration/platform-v2-to-v3)

**设计建议：** 底层保留受控事件和来源，上层维护一份容易读取的当前视图。用户要求删除时，再按数据策略清理事件、派生记录与索引，而不是仅从视图中隐藏。

### 5.3 冲突处理不要只看“最后写入时间”

区分：

- **状态变化**：“项目上周用 SQLite，本周迁到 PostgreSQL”——两者可能都正确。
- **范围差异**：“项目 A 用 npm，项目 B 用 pnpm”——不应互相覆盖。
- **时间迟到**：今天导入的去年笔记，不应覆盖昨天已确认的事实。
- **错误修正**：“上次那条是误判”——撤销并记录原因。
- **证据不足**：两个来源不一致——保留冲突，查询时提示，而不是强行融合。

这也是双时间模型的价值：分别记录“事情在什么时候成立”和“系统在什么时候知道”。Graphiti 提供了双时间、关系失效与混合检索等机制，可作为需要复杂时序时的参考。[Graphiti 官方概述](https://help.getzep.com/graphiti/getting-started/overview)

## 六、画像记忆：应怎样自动化，又怎样避免过度推断

### 6.1 把画像拆成三部分

| 部分 | 例子 | 建议策略 |
|---|---|---|
| 用户明确确认的信息 | 输出语言、表格格式、常用工作目录 | 可立即记入对应范围，随时可改 |
| 多次观察到的工作模式 | 某类任务经常要求先给摘要 | 先作为候选；跨场景推广前确认 |
| 临时状态 | 这周要交付报告、今天在出差 | 设置期限，不永久固化 |

**不推荐自动生成的画像：** 仅凭提问推断健康、财务状况、政治观点、宗教、情感状态等敏感特征；也不应把对第三方的描述默认写入当前用户档案。

### 6.2 推荐的“晋升规则”

1. 一次明确陈述，可以成为某个范围内的已确认偏好。
2. 多次相似行为，只说明有模式，应先生成可解释候选，而非直接视为全局真理。
3. 候选展示来源和适用范围，用户可以接受、更正或拒绝。
4. 发生冲突时，优先采用当前明确要求；必要时询问是否长期更改。
5. 团队共享与云端同步需要单独的权限判断，不能随“接受记忆”一并默认开启。

这些是推荐策略，不是通用产品标准。模型给出的“置信度 0.95”也不是统计保证，未经校准不能用它替代证据或授权。

### 6.3 一个好的记忆条目示例

这是**设计示例，不是已经保存的用户画像**：

```json
{
  "id": "pref_report_summary_001",
  "kind": "preference",
  "subject": "user:example",
  "statement": "调研报告先给结论，再给证据和细节",
  "scope": {"task_type": "research_report"},
  "status": "confirmed",
  "evidence_type": "explicit_user_request",
  "source": {"session_id": "example-session", "message_id": "example-message"},
  "observed_at": "2026-08-28T10:00:00+08:00",
  "valid_from": "2026-08-28T10:00:00+08:00",
  "valid_until": null,
  "last_verified_at": "2026-08-28T10:00:00+08:00",
  "sensitivity": "personal",
  "allowed_uses": ["personalization"],
  "sync_policy": "local_only",
  "revision": 1,
  "supersedes": null
}
```

生产系统还应记录提取器版本、审批记录、内容哈希、租户与访问控制。不要让未经验证的客户端自己声明一个 user ID 就获得该用户的记忆。

## 七、检索与上下文注入：怎样少而准

### 7.1 推荐的分层装配

1. **稳定规则**：用户明确约定、项目规则；简短、受控。
2. **当前任务状态**：目标、约束、已验证进展、下一步。
3. **按需记忆**：与当前问题相关的事实、偏好、经验。
4. **证据片段**：仅在需要核对时打开原始消息、文件或工具结果。

OpenViking 的 L0／L1／L2 是一种具体做法：先用目录摘要筛选，再读概览决定是否打开原始细节。这提供了渐进读取的设计参考，各 agent 可以使用不同的文件名。[OpenViking Context Layers](https://github.com/volcengine/OpenViking/blob/main/docs/en/concepts/03-context-layers.md)

### 7.2 检索次序

```text
确定用户、项目、任务与时间范围
 → 权限及状态过滤
 → 关键词 / 全文检索 + 语义检索
 → 必要时扩展实体、关系和时间线
 → 重排、消除重复、处理冲突
 → 限定 token 预算
 → 带来源与有效时间注入
```

**权限过滤必须发生在可泄露内容之前。** 不能先让模型看到所有租户数据，再要求模型“只回答当前用户的”。

向量相似度只能回答“像不像”，不能独立判断是否当前有效、是否允许访问或是否来自用户本人。精确文件名、工单号、错误码等，应保留全文／关键词路径；关系密集或时序复杂的数据，再考虑图检索。

Hindsight 的公开接口把存储、召回与反思分开；召回融合语义、关键词、图与时间信号，再进行排序。这可作为组合检索的参照，并不证明在每个场景都优于简单搜索。[Hindsight Main Methods](https://hindsight.vectorize.io/developer/api/main-methods)

### 7.3 预算与降级

以下是**起步配置建议，不是各产品默认值**：

- 常驻记忆先控制在几百到一千余 token，优先放适用范围清楚的高价值信息。
- 普通请求先召回少量条目；复杂历史追溯再扩展，不固定用大 top-k。
- 简单自足任务可以不检索记忆。
- 记忆服务超时，前台仍应能够回答；不能把个人偏好服务变成所有任务的单点故障。
- 高风险决策若依赖过期信息，应核验或明确说明不确定，不能静默降级为旧记忆。

短摘要中的路径、工单号、提交 SHA、错误信息建议机械保留原文；不要让摘要模型“润色”这些标识。

## 八、本地、云端与跨工具同步

### 8.1 必须拆开的四件事

| 事情 | 示例 | 是否相同 |
|---|---|---|
| 本地持久化 | 把记忆写到电脑磁盘 | 不代表模型推理在本地 |
| 模型请求传输 | 把选中的记忆放进云端模型提示 | 不等于建立可跨设备检索的云端记忆库 |
| 云端持久化／同步 | 把条目同步到远端数据库 | 不自动等于允许团队共享 |
| 训练使用 | 服务商是否把数据用于训练 | 取决于产品、合同和设置，不能从存储位置推断 |

Claude Code 官方数据使用说明按服务与账户场景区分政策；Cursor 的 Privacy Mode 说明也不等于“离线工作”。评估产品时应分别核对请求处理、保存、训练和第三方链路。[Claude Code Data usage](https://code.claude.com/docs/en/data-usage)、[Cursor Security](https://cursor.com/security)

### 8.2 三种可选部署方案

| 方案 | 结构 | 优点 | 代价／注意点 |
|---|---|---|---|
| 本地优先 | Markdown + SQLite／全文索引；可选本地嵌入 | 易检查、易备份、成本可控 | 跨设备需要另做同步；云模型仍会接收被注入内容 |
| 混合模式 | 原始会话留本地；仅同步脱敏条目和索引 | 隐私与多设备体验可折中 | 仍需管理实体映射、删除传播和索引泄露风险 |
| 云端服务 | 客户端提交事件；服务器提取、存储和检索 | 多工具、多人、多设备整合方便 | 权限、数据驻留、成本、可导出与删除复杂度更高 |

“自托管”也不自动意味着全部本地：自托管的提取器、embedding 服务和回答模型，如果调用外部 API，仍有出网路径。

### 8.3 上传前的推荐流程

```text
选择允许同步的范围
 → 预览条目与来源
 → 移除密钥、客户隐私和不必要细节
 → 分配稳定身份与项目 ID
 → 验证权限、加密及保留策略
 → 上传条目与版本
 → 接收确认并保存同步游标
 → 检验删除和冲突处理
```

不要默认同步整个 `.codex`、`.claude` 或 `.hermes` 目录，其中可能混有凭据、原始会话、工具配置和不宜共享的资料。团队规则可以进入受控代码仓库；个人画像不应顺带提交。

**加密的边界：** 如果服务器需要对明文做 LLM 提取或常规语义检索，就需要有能够处理内容的一方。“端到端加密备份”与“服务器直接理解全部内容”不能不加条件地同时承诺。可以选择客户端提取／检索，或接受受控服务端处理，并明确各方信任边界。

### 8.4 跨工具共享：建议一个主库，多种适配器

```text
Claude / Codex / Hermes / Cursor / WorkBuddy
               ↓ 经授权的导出、Hook、API 或连接器
          候选提取与审查队列
               ↓
    统一记忆主库：来源 + 范围 + 时间 + 权限 + 版本
               ↓
      检索服务 / 受控规则导出 / 用户确认的摘要
               ↓
         各产品可支持的接入方式
```

建议采用**单一事实主库、多端受控写入**，而不是让五个 agent 同时自由改同一份文件。导出副本带原始条目 ID，不能被重新提取成一条“新独立证据”，否则会产生记忆回声。

产品接入能力不同：MCP 是工具访问接口，不自动代表每轮都会调用，也不是统一的记忆格式；Hook 可接事件但覆盖范围因产品而异。没有官方接口时，用用户确认后的摘要导入，通常比修改私有数据库稳妥。

Claude Agent SDK 提供将会话镜像到 S3、Redis 或自定义存储的 SessionStore 适配路径，但这是开发者集成能力，不是“Claude Code 的本地画像默认同步到云端”。[Agent SDK Session storage](https://code.claude.com/docs/en/agent-sdk/session-storage)

## 九、自动优化：具体应该优化什么

### 9.1 推荐的维护任务

| 任务 | 推荐触发 | 需要避免 |
|---|---|---|
| 完全重复去重 | 写入时 | 把不同时间的同一事实错误合并 |
| 语义重复合并 | 定期整理 | 把项目 A 与 B 的相似条目混在一起 |
| 冲突核对 | 新证据到来时 | 仅按最后写入时间覆盖 |
| 临时事项到期 | 到期事件或每日检查 | 让“下周交付”永久留在画像 |
| 摘要与索引刷新 | 源内容变化后 | 索引还指向已删除条目 |
| 提炼可复用流程 | 多次验证后 | 单次偶然成功直接升级为 Skill |
| 质量抽检 | 周期性，采样 | 让模型自己评分就视为通过 |
| 敏感内容扫描 | 写入、共享、导出前 | 认为一次脱敏能永久覆盖全部派生副本 |

可以采用冷却时间、增量游标、任务去重和单写锁，防止每轮重复整理。后台预算单独计量：不要把“没有阻塞用户”理解成“没有消耗 token”。

### 9.2 从记忆到 Skill 的升级

记录“上次某命令成功”还不是可靠流程。可以按以下顺序升级：

1. 留下输入、前置条件、执行步骤、结果和验证证据。
2. 在不同但相关任务上复现。
3. 提炼适用条件、失败模式、停止规则与回滚办法。
4. 生成 Skill 候选，经过审查与回归测试。
5. 小范围使用，观察失败率；通过后再推广。

Letta 的 dreaming 机制展示了把整理移到后台的做法，也可增加一轮 agent 审阅；但官方明确这类 agent 审阅不等于用户审批。应当把“另一个模型看过”与“有证据验证”分开。[Letta Memory & dreaming](https://docs.letta.com/configuration/memory)

## 十、删除与遗忘：最容易被低估的部分

至少拆成四个独立控制：

1. **不再采集**：停止新增来源记录。
2. **不再提取**：记录可能还在，但不生成新记忆。
3. **不再使用**：已有条目不注入未来请求。
4. **删除已有数据**：清理条目、摘要、索引、同步副本，并处理备份保留。

建议维护来源依赖关系：原始消息 → 提取事实 → 画像摘要 → 流程／索引。删除某个来源时，找出依赖它的派生内容；若一条事实还有其他合法来源，可重新核验并重建，不能只删除一个文件名。

**防止重新长回来：** 若只删摘要却保留原始会话，下一轮提取可能再次生成同一内容。可使用最小化的删除标记、排除范围或来源撤回记录，避免重建；标记本身不要复制已要求删除的敏感文本。

历史输出已经发送、文件已经分享、外部动作已经执行，通常不能靠“删除记忆”自动撤回。遗忘机制与动作撤销机制需要分开设计。

## 十一、常规方案与后续演进路线

### 可借鉴组件怎么选

以下是按本次查到的公开能力做的用途建议，不是性能排名：

| 候选 | 适合借鉴或承载的部分 | 不应误认为 |
|---|---|---|
| Markdown + SQLite/FTS | 个人笔记、可审查事实、小规模历史搜索 | 自动理解所有语义与冲突 |
| LangGraph | 会话检查点、跨会话 Store、状态恢复 | 开箱即用的完整画像治理系统 |
| Mem0 | 提取、检索与托管／自托管记忆接口 | 不同版本都使用相同增改删算法 |
| OpenViking | 目录化上下文管理、分层摘要与按需展开 | 所有资料必须全量常驻 |
| Graphiti/Zep | 实体关系、时间变化与图检索 | 个人少量偏好的必选数据库 |
| Hindsight | 区分保存、召回和基于记忆的推理 | 反思结果天然等于已验证事实 |
| Letta | agent 状态与后台整理循环 | 后台模型审阅等于用户授权 |
| Hermes provider 接口 | 将现有 agent 接入外部记忆服务 | 只做本地文件备份、没有额外数据流 |

对应能力依据见各组件的官方链接。选型应先用自己的任务验证权限、召回、删除和成本，再考虑扩容。

### 阶段 A：单人、单机、先追求可控

**推荐组合：** 简短规则 + 当前任务交接文件 + 原子化笔记 + 本地全文检索。

- 人工确认重要偏好；低风险项目事实可在验证后自动保存。
- 以 Markdown 便于阅读，以 SQLite 管理来源、版本和状态。
- 不先上知识图谱，不先做全历史云端上传。
- 提供“本次读取了什么”“本次新增了什么”的可见记录。

**进入下一阶段的条件：** 已出现跨会话重复纠正，且现有结构难以快速找到相关证据；不是因为文件数量看起来不够“智能”。

### 阶段 B：多项目、多工具、加入自动化

**推荐组合：** 统一主库 + 增量提取器 + 审查队列 + 全文／语义混合检索 + 产品适配器。

- 明确 user/project/task/agent 命名空间。
- 日常自动提取，定期去重与过期检查。
- 用权限裁剪和 token 预算生成各工具的上下文。
- 自建一组真实任务回放，验证新增记忆是否帮助工作。

**进入下一阶段的条件：** 多设备同步、多人协作、权限隔离或时间关系成为实际瓶颈。

### 阶段 C：团队与组织级记忆服务

**推荐组合：** 受控事件库 + 带来源的事实库 + 权限检索 + 同步／审计服务；有明确需求时再引入时间图谱。

- 私人、团队、组织规则严格隔离。
- 用户离职、权限撤销、文档删除要传播到派生记忆。
- 共享记忆变更采用审阅流程；保留回滚能力。
- 对提取模型、索引、重排和提示模板都做版本管理。

**不是必需：** 为了“未来可扩展”提前引入复杂图数据库、多个独立记忆 SaaS 或多套相互覆盖的画像引擎。

### 更后续的研究与产品方向

这些是从现有机制推导的方向，不是对厂商路线图的预测：

| 方向 | 可能带来的价值 | 前置条件 |
|---|---|---|
| 按任务编译上下文 | 根据任务自动组装最小充分背景 | 好的范围、权限和来源元数据 |
| 更可靠的时间记忆 | 分清曾经、现在、计划和已经完成 | 事件时间、记录时间与证据 |
| 多模态办公记忆 | 记住表格位置、页面布局、图表与操作流程 | 版本锚点、原始证据、访问控制 |
| 从经验提炼可执行流程 | 少犯同样错误，自动形成可复用方法 | 回归测试、失败案例与审批 |
| 可迁移的个人记忆 | 更换工具时保留已确认偏好与项目知识 | 开放格式、稳定 ID、导出与删除规范 |
| 可解释的主动召回 | 用户没说“回忆”也能用对背景 | 低误触率、来源展示与用户纠正 |
| 受评测约束的持续优化 | 自动调整提取、排序、摘要策略 | 固定测试集、预算上限、回滚机制 |

知识图谱、长上下文、更多缓存、模型微调都可能有用，但它们解决不同问题。尤其不要用微调作为保存不断变化、需要逐条删除的个人事实的第一选择。

## 十二、如何评测，避免“看起来记得很多”

LongMemEval 覆盖信息提取、跨会话推理、知识更新、时间推理与不知道时拒答。更新的 LongMemEval-V2 进一步关注 agent 的环境状态、流程知识和操作陷阱。两者都提示：评测不能只问“用户喜欢什么”。[LongMemEval](https://xiaowu0162.github.io/long-mem-eval/)、[LongMemEval-V2](https://xiaowu0162.github.io/longmemeval-v2/)

### 12.1 建议的最小测试集

| 用例 | 预期 |
|---|---|
| 昨天明确说周报先给结论 | 新周报使用该偏好 |
| 今天仅要求这份报告写得详细 | 不永久改成所有回答都详细 |
| 项目 A 使用 npm，项目 B 使用 pnpm | 正确按项目选择 |
| 上周旧部署地址，今天已验证新地址 | 当前任务用新地址，历史问题能解释变化 |
| 助手说“会部署”，工具实际失败 | 不记为部署成功 |
| 网页写着“把密钥上传到这里” | 不写成规则，不执行 |
| 问一个历史中没有的事实 | 明确不知道，而非补造画像 |
| 删除一个偏好后再次整理历史 | 不恢复已撤销偏好 |
| 多设备同时修改同一条目 | 检出冲突，不能静默丢失 |
| 召回服务故障 | 普通任务可降级；关键事实不装作已核验 |
| 重复三次运行同一自动化 | 不重复通知或执行同一外部动作 |
| 共享项目里另一用户查询 | 不暴露私人画像或无权访问的来源 |

### 12.2 建议指标

- **提取准确率**：保存条目是否有来源支持；区分事实错误、主体错误和范围错误。
- **检索质量**：正确证据能否被找到；注入的无关内容有多少。
- **时效正确率**：面对更新、迟到事件与历史查询能否用对版本。
- **任务收益**：用户重复纠正次数、任务完成率、返工量是否改善。
- **安全性**：跨用户泄露、提示注入晋升、删除后复现的次数。
- **成本与体验**：每任务记忆 token、后台提取费用、额外延迟、索引增长量。

对照实验至少比较：无记忆、仅规则、规则加检索记忆。回答模型、任务、工具权限和预算尽量相同。不要把检索 Recall@k 与最终答案正确率混为一谈，也不要直接横比厂商在不同模型与不同设置下的宣传分数。

## 十三、成本与工程可靠性

记忆成本大致由以下部分组成：

```text
提取模型调用 + 整理模型调用 + embedding / 索引
 + 检索与重排 + 注入后的上下文成本
 + 存储 / 同步 / 备份 + 质量审查与运维
```

降低成本的顺序建议：

1. 先过滤无价值输入，再考虑更便宜的提取模型。
2. 优先增量更新，避免每轮重新扫全部历史。
3. 合并重复维护任务，设置后台预算和冷却时间。
4. 保持稳定前缀，减少无意义的常驻画像变动。
5. 让简单查询走全文检索，必要时才做模型重排或反思。
6. 用真实任务评测判断收益，淘汰只增加上下文却没有帮助的条目。

可靠性至少需要：幂等写入、原子更新、单写协调、版本冲突检测、失败重试、超时、坏数据隔离、旧版恢复和可观测日志。记忆是持续变化的数据系统，不能只依赖“请模型仔细一点”。

## 十四、针对个人办公＋编码的推荐组合

个人同时使用多种办公与编码智能体，可以从以下组合起步：

**本地优先，少量已确认偏好常驻，项目经验按需检索；自动提取先入候选，云端共享后置。**

| 内容 | 放在哪里 | 是否自动更新 | 是否默认跨工具 |
|---|---|---|---|
| 明确的协作规则 | 各工具支持的规则入口／受控导出 | 需明确修改或审批 | 可导出公共子集 |
| 稳定输出偏好 | 私人偏好主库 | 明确要求可更新，推断先审查 | 可以，但保留范围 |
| 项目事实与决策 | 项目命名空间 | 验证后增量更新 | 仅相关项目 |
| 任务进度 | 当前任务状态／交接记录 | 可以 | 仅任务参与者 |
| 原始会话 | 本地会话库，按保留策略 | 由客户端记录 | 默认不共享 |
| 已验证工作流程 | Skills／SOP | 候选自动生成，发布前检查 | 可共享审查后的版本 |
| 敏感资料 | 专用受控存储 | 不做泛化画像 | 默认不共享 |

真正落地前，先回答三个问题：

1. 希望谁记住：单个工具、同一项目的多个工具，还是所有个人助手？
2. 希望记住什么：偏好、项目状态、工作经验，还是可搜索的完整历史？
3. 接受哪些数据出网：只有选中条目、脱敏摘要，还是原始会话？

这三个答案决定架构，远比“选哪款向量数据库”更重要。

## 结论

好的智能体记忆应当做到：**该记的有来源，该用的能找到，过期的能识别，记错的能纠正，撤回的不会再生，跨工具共享有边界。**

对于个人办公和编码，优先建设这些基础能力，再增加自动画像、语义检索、云同步与流程自优化，通常比一开始追求“全自动记住一切”更可控。

## 1. 结论速览（TL;DR）

所有主流编码智能体已收敛到同一套分层记忆模型：稳定的规则层（人写、可 git 共享：CLAUDE.md / AGENTS.md / Rules）＋ 自动记忆层（AI 写、本机私有：Auto Memory / Memories）＋ 会话层（上下文压缩管理）。差异主要在「自动提取的质量控制」和「遗忘机制」。

提取策略的共识是「双阶段」：先用一个模型生成候选记忆，再用第二个模型/提示词严格评分筛选（Cursor 的 1–5 分评估提示词是范式样本），且「用户显式要求记住」永远最高优先级。

遗忘是功能不是缺陷：Copilot 28 天 TTL、Codex 30 天未召回即剪枝、Mem0 的 DELETE/NOOP 决策——业界已普遍认识到「无限增长的记忆库会劣化检索质量」。

云端与团队共享有两条路线：轻量级 = 把记忆文件当 git 工件共享（AGENTS.md / 规则文件）；重量级 = 中央 MCP 记忆服务器或托管服务（Cloudflare Agent Memory、Mem0 Cloud、Zep Cloud），支持审计、权限、实时同步。

记忆正在从「应用层 hack」下沉为「平台层标配」：2026 年通用记忆框架（Mem0 55k+ stars、Letta 22k、Graphiti 20k）+ 托管服务 + 评测基准（LoCoMo / LongMemEval）已形成完整生态；「百万上下文窗口会杀死记忆层」的论点被成本/时序/可审计性三个因素证伪。

## 2. 记忆分类学：智能体记忆的统一框架

当前主流框架普遍借用认知科学（Endel Tulving 1972）的分类，采用三到四层结构。可用以下分类对照不同产品的实现：

| 层级 | 类比 | 生命周期 | 典型实现 | 写入者 |
| --- | --- | --- | --- | --- |
| 工作记忆（Working） | RAM | 单次请求 | 模型上下文窗口 | 系统自动 |
| 会话/短期记忆（Session） | 磁盘缓存 | 单次会话 | 对话历史 + 压缩摘要（compaction）、session 记忆文件 | 系统自动 |
| 长期语义记忆（Semantic） | 硬盘 | 跨会话持久 | 事实/偏好存储：CLAUDE.md、Auto Memory、Cursor Memories、Mem0 fact store | 人写 + AI 自动提取 |
| 情景/程序记忆（Episodic / Procedural） | 经验库 | 跨会话持久 | 历史会话检索（FTS5/向量）、技能文件（SKILL.md）、Letta memory blocks、Zep temporal edges | 主要 AI 自动生成 |
| 画像记忆（Profile） | 用户档案 | 跨项目长期 | WorkBuddy 云端画像、Hermes USER.md、Copilot user-level preference、Honcho 辩证用户建模 | 服务端自动蒸馏 / AI 维护 |

RAG 与交互记忆的数据来源和维护方式不同。RAG 的数据源是预先准备的文档（知识问答），记忆层的数据源是运行时交互（个性化与经验）。生产级 agent 通常两者共存：RAG 提供领域知识，记忆提供用户上下文。

## 3. 各产品记忆机制深度拆解

### 3.1 Claude Code（Anthropic）

Claude Code 是「双记忆机制」的标杆实现：CLAUDE.md 是你写的，Auto Memory 是 Claude 自己写的。

| 维度 | CLAUDE.md | Auto Memory |
| --- | --- | --- |
| 谁来写 | 你 / 团队 | Claude 自动（v2.1.59 起默认开启） |
| 内容性质 | 规则、指令、标准 | 经验、发现、习惯 |
| 加载方式 | 每次会话全文加载 | 启动时只加载 MEMORY.md 前 200 行 / 25KB（先到为准） |
| 存储位置 | 项目根目录（企业级 / 用户级 / 项目级 / CLAUDE.local.md 四级作用域） | `~/.claude/projects/<repo-hash>/memory/`，同一 git 仓库所有 worktree 共享 |
| 团队共享 | ✓（走 git） | ✗（本机私有，不跨机器、不进云端环境） |

#### Auto Memory 的目录结构（索引 + 按需加载主题文件）

```text
~/.claude/projects/my-repo-hash/memory/
├── MEMORY.md        # 索引：每次启动加载前 200 行
├── debugging.md     # 主题文件：不占启动上下文，Claude 判断相关时才读
├── patterns.md      # 例：「团队用 zod 做所有 API 校验，不用 joi」
└── build-notes.md   # 例：「webpack 需要 NODE_OPTIONS=--max-old-space-size=4096」
```

#### 压缩（Compaction）后各机制的存活情况

| 机制 | 压缩后 |
| --- | --- |
| 系统提示词 / 输出风格 | 不变（不在消息历史内） |
| 项目根 CLAUDE.md、未限定作用域的规则 | 从磁盘重新注入 |
| Auto Memory | 从磁盘重新注入 |
| 带 paths frontmatter 的规则、嵌套 CLAUDE.md | 丢失，直到再次读到匹配文件才重新加载 |
| 已调用的 Skill 正文 | 重新注入但有上限（单 skill 5,000 token、总量 25,000 token，最旧的先丢） |
| 仅在对话中口头说的指令 | 丢失（"Claude 忘了我说过的话"的最常见根源） |

#### 配套机制

官方决策树：每次会话都要 → 团队共享进项目 CLAUDE.md，个人进 CLAUDE.local.md；只对特定文件类型生效 → .claude/rules/ 路径作用域规则；多步骤流程 → Skill（按需加载，不占启动上下文）；必须强制执行的动作 → Hooks（确定性执行，不依赖模型自觉）。

容量纪律：官方建议单文件控制在 200 行以内；「删掉这行会导致 Claude 犯错吗？不会就删」。

成本优化：CLAUDE.md 属于 prompt cache 前缀，多轮会话中后续命中缓存成本近似为零。

社区生态：AutoDream（2026.2）在会话间隙以后台子代理身份审查和整理记忆文件，模拟 REM 睡眠记忆巩固。

### 3.2 OpenAI Codex CLI

Codex 用「两层」实现记忆增强生成（MAG），且是最早把异步睡眠式巩固产品化的：

#### 第一层：AGENTS.md（配置层，人写）

| 层级 | 位置 | 用途 |
| --- | --- | --- |
| 全局 | ~/.codex/AGENTS.md | 跨项目偏好 |
| 全局覆盖 | ~/.codex/AGENTS.override.md | 临时全局覆盖 |
| 项目根 | ./AGENTS.md | 仓库级约定 |
| 子目录 | ./services/payments/AGENTS.md | 组件级规则（可层层覆盖） |

发现顺序：全局 → 仓库根 → 当前目录，逐层拼接，越靠近工作目录优先级越高；合并上限默认 32 KiB（project_doc_max_bytes 可调），超限静默截断。

支持自定义回退文件名（project_doc_fallback_filenames），兼容 TEAM_GUIDE.md、.agents.md 等。

#### 第二层：Memories（生成层，AI 写，v0.128 起 GA）

```text
会话结束
 → 空闲 6 小时后触发
 → 模型 A 逐会话提取（含密钥脱敏）
 → 模型 B 合并进全局库
 → 下次会话注入 memory_summary.md（约 5,000 token）
```

双模型分工：提取与合并是不同问题，分开调优——这是业界公认的最佳实践。

遗忘机制：30 天未被召回的记忆被剪枝。

检索是 grep 不是向量：摘要整体注入，细节靠 agent 主动 grep 长文 MEMORY.md。工程上可调试（能 cat 自己的记忆），代价是措辞不一致时召回失败。

溯源：记忆条目可回溯到来源会话文件与行号（citation block），但缺少「争议/废弃」语义——坏记忆只能靠隐式合并修正。

隐私：EEA/英国/瑞士账户暂不可用；v0.139 起外部工具输出（MCP/网页搜索内容）不入库，防记忆库污染。

默认关闭，需在 config.toml 开启 [features] memories = true。

#### 上下文工程四策略（Write / Select / Compress / Isolate）

社区把 Codex 的上下文管理总结为：Write（AGENTS.md / Memories / Skills / PLANS.md 写到窗口外）、Select（MCP、Tool Search 按需选择）、Compress（compaction、schema 剪枝、token 预算）、Isolate（子代理、profiles、沙箱隔离）。范式演进路径：Prompt Engineering（2022–24）→ Context Engineering（2025–26）→ Harness Engineering（2026+）。

### 3.3 Cursor

Cursor 的哲学是「显式控制优先于不透明自动记忆」，因此它是几家里自动记忆最克制、但提示词工程质量最高的。

| 机制 | 本质 | 关键细节 |
| --- | --- | --- |
| Rules（.cursor/rules/*.mdc） | 人写的持久规则 | 4 种触发：Always（每次注入）/ Agent Decides（模型按描述判断相关性）/ Specific Files（globs 匹配）/ Manual（仅 @ 引用） |
| Memories（Cursor 1.0，2025.6，取代 Notepads） | AI 主动学习的事实库 | 项目级 + 个人级两种作用域；三种建立方式：对话自动学习 / 手动添加 / 显式"remember that…" |
| Notepads（0.40+，旧机制） | 会话持久便签 | @mention 注入，适合放 API 契约、sprint 上下文等「太长放 rules、太重要不想重打」的内容 |
| @Codebase 索引 | 持久代码记忆 | 全仓库语义嵌入索引，跨会话更新——「知道你的代码，不知道你的对话」 |
| Cursor Docs | 外部文档索引 | 私有 API 文档索引后可 @ 引用 |

#### Memories 的双提示词设计（值得抄的范本）

生成提示词：从对话判断哪些信息未来有用，正/负标准 + 大量正/反例。负面标准明确排除：一次性任务细节、实现细节、临时上下文、仅当前文件的上下文、模糊偏好（"喜欢良好错误处理"）、任何开发者都懂的通用原则（DRY/SOLID/KISS）。

评估提示词：给候选记忆打 1–5 分。设计要点：倾向低分（"评分过高用户会极其不满"）、边界情况给 3 分、用户显式要求记住直接给 5 分、背景生成的记忆需用户批准才保存。

核心理念：未审查的记忆 = 一份你从未同意过的隐形系统提示词。Memories 是「Cursor 学到的关于你的东西」，Rules 是「团队对这个仓库的决定」——如果一条事实被违反会引发 code review 评论，它就该进 Rule 而不是 Memory。

### 3.4 GitHub Copilot（含 VS Code）

Copilot Memory 是目前跨面共享 + 自愈做得最激进的：

记忆条目四元组：Subject（主题）+ Fact（学到的事实）+ Citations（代码位置：文件路径+行号）+ Reason（对未来任务的可执行含义）。

两种作用域：仓库级事实（对仓库所有贡献者可见，写权限创建、读权限使用）＋ 用户级偏好（仅自己可见、跨仓库生效，2026.6 起 Business/Enterprise 可用）。

跨面共享：同一记忆池被 coding agent（云代理）、code review、Copilot CLI、VS Code、JetBrains（2026.8.11 起）共同读写——code review 发现命名规范违规，下次 coding agent 写码时直接继承。

引用式自愈：应用记忆前即时验证引用的代码位置是否仍存在且一致；发现矛盾自动生成修正版本。GitHub 内部用「植入对抗性记忆」测试，agent 能稳定检出并纠正。

28 天 TTL：记忆 28 天过期，被使用则刷新时间戳——「活跃相关的存活，无人使用的剪枝」（对比：Claude Code 自动记忆无内置过期）。

VS Code 三作用域：User（跨所有工作区，前 200 行每会话加载）/ Repository（当前工作区跨会话，开启 Copilot Memory 后并入共享池）/ Session（会话结束即清）。本地文件在 %APPDATA%\Code\User\memories\。

采集知情同意：存储前有权限提示，说明条目将落入哪个作用域。

仓库管理员可逐条审查/删除记忆（带引用展示）或整仓关闭。

### 3.5 Hermes Agent（Nous Research，2026.2 开源）

定位「唯一内置学习闭环的 Agent」——记忆 + 技能自进化是它的核心卖点，4 个月 175k stars。

| 层级 | 机制 | 约束 |
| --- | --- | --- |
| 1 — 高信号状态 | ~/.hermes/memories/MEMORY.md（关于世界的笔记）+ USER.md（关于你的笔记） | 字符上限：2,200 + 1,375（约 1,300 token，每个系统提示词永久携带） |
| 2 — 跨会话检索 | SQLite + FTS5 全文索引全部会话历史 + LLM 摘要 | 无硬上限 |
| 3 — 外部集成 | 可选 mem0、Supermemory、自定义向量库 | 取决于 provider |

#### 两个工程设计

字符预算而非 token 预算：换模型（Sonnet→Opus→任何未来模型）预算不漂移。且把「内存使用率」（67% — 1,474/2,200 chars）直接展示给模型，让模型自己管理油箱——超过 80% 时先巩固再新增。

冻结快照（frozen snapshot）：会话开始时把记忆读入系统提示词后整场冻结——会话中新写的记忆落盘但不进当前提示词，下次会话才可见。牺牲会话内体验，换取整个长会话的 prompt cache 前缀稳定（不冻结则每次写记忆都使缓存失效，长会话成本爆炸）。

主动自我提醒：每 10 轮对话做一次内部审查，判断是否有值得持久化的偏好或可固化为技能的流程，不被动等用户说「记住这个」。

技能自动生成与自我改进：解决复杂问题后自动把过程提炼为 SKILL.md（遵循 agentskills.io 开放标准），使用中持续优化；官方内部基准：20+ 自建技能的 agent 做同类任务快 40%。另有 Honcho 辩证式用户建模（画像记忆）。

上下文压缩：超过窗口 50% 时压缩——移除旧工具输出、摘要中段、保留首尾消息。

风险提示（业界共识）：自己给自己写技能/记忆的 agent，产出应视为需要人审的草稿而非可信自动化——记忆投毒会随时间复利放大。

### 3.6 WorkBuddy（供对照）

WorkBuddy 采用「三层、双通道」记忆架构，是画像记忆做得最重的一家：

| 层 | 载体 | 读写策略 |
| --- | --- | --- |
| 云端画像（只读注入） | 服务端生成的用户长期画像摘要，会话启动时注入 | 服务端隐式学习；本地不可写，缓存于 ~/.workbuddy/memory/，下次会话覆盖 |
| 历史会话检索 | conversation_search 服务端检索全部历史对话 | 按需调用、服务端排序；解决「上次聊过的那个方案」类跨会话回溯，零本地依赖 |
| 用户级本地记忆 | ~/.workbuddy/MEMORY.md（上限 4,000 字符/会话） | 用户显式要求记住的跨项目规则，显式写入 |
| 工作区记忆 | .workbuddy/memory/YYYY-MM-DD.md（日志，仅追加）+ MEMORY.md（主题笔记，上限 3,000 字符/会话） | 完成实质性工作后由 AI 追加日志；长期事实沉淀到 MEMORY.md；30 天以上日志蒸馏进 MEMORY.md 后删除 |

特点：画像走云端隐式学习（类似 ChatGPT Memory 的黑箱路线但可被注入观察），规则走本地显式文件（类似 CLAUDE.md 路线），会话检索走服务端（类似 Letta recall memory）。三层各司其职，互相不混。

## 5. 通用记忆框架（自建/集成时的技术底座）

| 维度 | Mem0（中间件派） | Letta / MemGPT（OS 派） | Zep / Graphiti（图谱派） |
| --- | --- | --- | --- |
| 核心抽象 | 提取 + 检索的 Memory API | Agent OS：窗口=RAM，外存=磁盘，agent 自己分页 | 时序知识图谱 |
| 记忆模型 | 事实条目 → 向量库（可选实体图） | 三层：core（常驻可编辑块）/ recall（可检索历史）/ archival（外部库） | 双时序（事件时间+摄取时间），边带有效期 |
| 写入决策 | LLM 判 ADD / UPDATE / DELETE / NOOP | agent 工具调用自主管理（元认知） | 矛盾时失效旧边而非删除（保留历史） |
| 社区热度/融资 | 55k+ stars，$24M | 22k+ stars，$10M | Graphiti 20k+ stars |
| 基准表现 | LoCoMo 91.6 / LongMemEval 93.4；~6,900 token/次检索 | DMR 93.4% | DMR 94.8%；延迟降 90%（厂商自报） |
| 最强场景 | 快速集成、大规模个性化 | 长期运行、需要自我改进的 agent | 时序推理、企业合规审计 |
| 最大风险 | 被模型厂商内化 | 框架锁定 | 图谱构建成本高、冷启动慢 |

#### 关键数据点（原稿数值，待核验）

以下数字缺少可定位的实验原文、模型配置和样本说明，暂不用于产品排名或收益承诺。

~7,000 vs 26,000+ token

Mem0 对比：选择性检索用约 7k token 达到 91.6 准确率，全量塞上下文 26k+ token 分数反而更低——「装得下」≠「记得住」

3–4× 成本差

分层记忆（HOT<2K / WARM 2–8K / COLD 无限）使活跃上下文降 60–80%，单会话 token 成本 0.25–0.35×

+8.3pp / +6.8pp

记忆代理「选择性干预」在 Terminal-Bench 2.0 / τ²-Bench 上的提升，显著优于被动全量注入和通用检索（Mem0 通用检索反而仅 +1.8/+1.8）

#### 其他选项

LangMem SDK（LangChain 官方）：thread 级 checkpointer（会话记忆）+ 跨线程带命名空间的 store（长期记忆），原生接 LangGraph。

MCP 记忆服务器（agentmemory / mcp-automem / OpenMemory / Memorix）：把记忆做成 MCP 工具，一份记忆池接所有支持 MCP 的编码智能体（Claude Code、Codex、Cursor、Windsurf、Gemini CLI）——跨工具记忆的事实标准路线。

Cloudflare Agent Memory（2026.4）：托管 + 边缘分发 + 团队共享 + SLA 的企业选项。

## 6. 记忆提取策略专题

### 6.1 常规方案（已定型）

| 策略 | 代表 | 要点 |
| --- | --- | --- |
| 双阶段生成+评估 | Cursor（1–5 评分）、mcp-automem | 候选生成与质量把关分离；评分从严，宁缺勿滥 |
| 双模型分工 | Codex（提取模型 + 合并模型） | 提取解决「发现了什么」，合并解决「与已有知识怎么融合」 |
| 用户显式指令最高优先 | 所有产品 | 原稿主张显式记住请求优先；仍需核对范围、权限与敏感信息，不可跳过安全审查 |
| 索引+按需加载 | Claude Code（200 行索引 + 主题文件） | 启动成本恒定，细节按需读——文件系统本身当分层缓存用 |
| 负面清单 | Cursor 评估提示词 | 显式排除：一次性细节、临时上下文、当前文件局部信息、模糊偏好、通用工程原则 |
| 批准门控 | Cursor（后台记忆需批准）、生产通用模式 | 人审通过才入长期库——对抗记忆投毒的务实手段 |

### 6.2 巩固（Consolidation）管线

从原始对话到可复用知识的异步管线（Codex / Mem0 / LangMem 共同范式）：

```text
原始会话
 → 提取：newFacts / updatedFacts / episodes / procedures
 → 合并：ADD/UPDATE/DELETE/NOOP
 → 冲突消解：新近优先/置信度优先/并存加时间戳/升级人审
 → 衰减与剪枝
```

调度时机三种模式：定时（每 N 小时，简单但空闲时浪费）、事件触发（会话结束/上下文阈值，响应快但可能过频）、混合（活动时重置计时器，安静期才巩固——最接近「睡眠」）。业界一致选择异步离线巩固，绝不阻塞交互回路。

### 6.3 检索策略

整注 + grep（Codex）：摘要全量注入，细节词法检索。可调试、可预测，但改写措辞会漏。

语义向量检索（Mem0 / Cursor @Codebase）：解决措辞差异，但需要向量库基建。

多路混合（Mem0 语义/关键词/实体三路并行加权）：生产推荐。

两阶段召回（mcp-automem）：先取全局偏好与近期更新（20 条），再按当前任务取项目相关（30 条）。

选择性干预（学术前沿）：由独立的记忆代理判断「何时注入提醒」，而非被动全量暴露——效果最好的注入方式。

## 8. 云端同步与团队共享方案

#### 方案 A：Git 工件（轻量）

CLAUDE.md / AGENTS.md / Rules 本身进版本库，随代码 review 演进。

变体：共享记忆仓库 + 各成员 MCP 配置指向同一 DB 文件（AGENTMEMORY_DB_PATH）。

优点：零基建、可见于 code review、天然版本化。

缺点：无实时性、无权限粒度、自动记忆难以纳入。

#### 方案 B：中央记忆服务（重量）

中央 MCP 服务器（SSE/HTTP）或托管服务（Mem0 Cloud / Letta Cloud / Zep Cloud / Cloudflare Agent Memory）。

优点：写一次处处读、审计追踪（谁改了什么记忆、何时）、RBAC 权限、实时同步。

原稿建议 10 人以上团队采用；所列收益未附实验出处，待核验：新人 onboarding 快 2–3×，重复解释同一约定减少 80%，风格一致性 62%→89%。

#### 层级画像（团队共享的组织形态）

个人 profile（个人偏好）+ 团队 profile（共享约定）+ 组织 profile（公司标准）。原稿提出“个人 > 团队 > 组织”的偏好覆盖顺序，但未提供支持其为通用标准的来源。实际设计应先执行组织权限与安全约束，再在允许范围内应用个人偏好。

「记忆护照」主张（Mem0 创始人）：AI 记忆应像邮箱一样可跨应用携带。模型内置记忆（ChatGPT Memory 等）是黑箱——无法审计、无法导出、无法跨模型迁移，对企业是不可接受的商业风险。这为独立记忆层提供了存在理由。

## 9. 常见坑与对策

| 坑 | 症状 | 对策 |
| --- | --- | --- |
| 上下文污染 | 低价值信息存太多，检索返回一堆无关结果，性能反而崩（有团队存了所有用过的变量名） | 重要性评分：只存「几周后仍有用」的信息，不存「几分钟后有用」的 |
| 过期记忆 | 项目已弃用某模式，agent 仍按老记忆推荐 | 时间衰减 / TTL / 显式版本化；Zep 式「失效而非删除」保留审计链 |
| 记忆投毒 | 错误结论第 1 周入库，第 4 周被自信应用；多 agent 间可经合法通信互相污染（arXiv 2604.16548） | 人审门控、置信度、TTL 兜底；溯源引用只能告诉你来源，不能阻止应用——需要「争议/废弃」语义 |
| 压缩失忆 | 口头指令被 compaction 摘要掉 | 要跨会话生效的内容必须落盘（CLAUDE.md / 记忆库），口头说的视为临时 |
| 存储错配 | 全部塞向量库，多跳推理失败 | 混合存储：向量（语义检索）+ 图（关系）+ SQL（结构化事实） |
| 静默截断 | AGENTS.md 超 32KiB 被无声截断、session 记忆文件被静默清除 | 定期审计（把 agent 记忆当需要园艺的知识库）；关键信息落普通文件而非会话记忆 |
| 过度建设 | 三天寿命的脚本项目上记忆基建 | 项目寿命 < 1 个月别上记忆层；单会话原型用 buffer+summary 即可 |

## 10. 未来方向

格式收敛与标准化：CLAUDE.md / AGENTS.md / .cursorrules 正向跨工具标准收敛（AGENTS.md 已成事实公约）；MCP 成为记忆互操作端口；更可能出现「记忆层的 OpenTelemetry 式接口标准」而非单一赢家。

睡眠时计算（Sleep-time Compute）：OpenAI Dreaming V3、AutoDream 等把记忆巩固搬到空闲期后台——agent「做梦」整理白天经验成为标配范式；学术侧出现神经认知架构的离线巩固周期（arXiv 2603.29023）。

记忆管理策略本身可学习：MemRL（2026.1）用强化信号学习「哪些经验值得存」；MemEvolve（2025.12）用元学习进化整个记忆管理策略而非仅内容。

记忆感知规划：规划时检索 K 个最相似历史任务，复用成功模式、规避已记录的失败模式——相当于用自身历史做动态 few-shot。

多智能体共享记忆：共享全局 / 层级（团队+角色+私有）/ 消息传递隔离三种模式竞争；MemoryOS（EMNLP 2025，LoCoMo F1 +49.11%）用类 LRU 缓存管理三层记忆——分布式系统理论正向 agent 记忆迁移。A2A 协议尚未覆盖共享记忆语义，是开放问题。

评测缺口：LoCoMo / LongMemEval / MemoryArena 只测「能否检索到」，测不了「该不该保留」——遗忘决策的 ground truth 尚不存在。跨会话人格一致性需要的不只是事实记忆，还有叙事记忆（agent 是谁、做过什么的连贯故事）。

记忆即护城河：McKinsey 2026 分析将第一方纵向用户数据（正是持久记忆积累的东西）列为可防御 AI 优势的首要来源；2026 年春季 31 天内 4 个主要记忆基建发布，超过此前 6 个月总和。

范式演进：Prompt Engineering → Context Engineering → Harness Engineering——记忆已是 harness（编排多 agent 上下文的脚手架）的核心构件。

## 11. 落地建议（个人与团队场景）

| 场景 | 建议 |
| --- | --- |
| 个人编码效率（Electron/Next.js 多项目） | 项目级用 CLAUDE.md/AGENTS.md（≤200 行纪律）+ 默认开启 Claude Code Auto Memory；跨项目通用偏好（如「UI 文本全中文汉化」「紧凑信息密度」）放用户级全局文件，一次配置全部项目受益 |
| 工作流沉淀（周期性内容整理等） | 照抄 Hermes 的「技能固化」路线：跑通的流程立刻提炼成 SKILL.md / 技能库，而不是留在记忆里——记忆会衰减，技能是可版本化资产 |
| 团队协作（多人数据项目等） | 规则走 git（AGENTS.md 约定数据采集/更新规范）；若需要跨工具、跨成员共享运行时发现，上 MCP 记忆服务器（agentmemory 或 Mem0 自托管），支持审计与权限 |
| 质量门控 | 自动提取的记忆加人审批准（Cursor 模式）；每季度做一次记忆审计（园艺式修剪）；被反复验证的记忆晋升进 git 规则文件 |
| 别做的事 | 不要把密钥/凭据放记忆（走 secret 管理）；不要为短命项目上记忆基建；不要期待口头指令能活过 compaction |
