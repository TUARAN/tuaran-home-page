> 这样下去，除了少数例外，**每一层最终都会变为当下最流行的解决方案**。前端趋向 React，系统趋向 Rust，脚本趋向 Python，甚至连页面本身都趋向 Next.js，完全无视适配性。
>
> ——Ryan Carniato，《Nobody Argued For Your Stack》，中文译文

这段话让我在意的，是技术选型的依据正在发生什么变化。一个工具被反复生成、反复展示，久而久之，就可能省略掉“它适合什么问题”这一层讨论。

原作者：**Ryan Carniato**，发表于 Playful Programming / DEV Community。英文原文：[Nobody Argued For Your Stack](https://dev.to/playfulprogramming/nobody-argued-for-your-stack-51fj)。

### 技术栈更替带来的刺痛

上周，Cursor 已经基本完成从 SolidJS 向 React 迁移的消息传开了。这次迁移大约发生在七个月前，但在 Solid 2.0 RC 发布之后，它成了讨论的焦点。又过了一周，也就是昨天，我注意到 Anthropic 文档里，用来演示大规模迁移功能的示例命令竟然是这样的：

我承认，我的第一反应很不好。有那么多例子可以选，偏偏选了这个……就在我们发布项目有史以来最大一次更新的同一周，我多年的工作成了“你应该从它迁走”的标准示例。那种刺痛，我不会假装不存在。我的第二反应是，这大概和那一周看到的其他跟进文章一样，追着一周前的新闻跑。

随后我查了互联网档案馆，发现这个例子至少从 2026 年 4 月就在那里了，比 Cursor 的消息传开早了四个月。当时，公开信息只有 Cursor 一月份一篇博客里夹在几项更大更新之间的一句实验说明。圈外人恐怕根本不会留意。没有理由，没有基准测试，没有论证。

停下来想想，这意味着什么。我得谨慎一点：我无法证明 Anthropic 的任何人读过 Cursor 那篇博客，谁也无法证明。也许某位文档作者看到了那个实验，也许 Claude 自己起草了这个例子。但想一想：要么是一家公司发布说明里不起眼的一句话，传进了另一家公司的官方文档；要么根本不需要这样的源头。在任何公开迁移案例出现之前，这个方向就已经被当成理所当然。

我们的行业悄悄发生了变化：过去传播论证的地方，如今开始广播结论。时机糟得不能再糟，因为正如后面要谈到的，论证是如今唯一仍然重要的依据。

### 为什么这比过去更重要

你完全可以问：以前不也这样吗？团队盲目模仿大公司，“Netflix 或 Facebook 在用”这种说法，比 AI 早了几十年。形象和组织政治一直可能压过纯粹的技术价值。Facebook 的影响力，也确实帮助了 React 早期的传播。

但过去，一套叙事要落地，总会遇到阻力。它一直参与竞争，却没法轻易甩开论证。如今，这一点变了，原因有两个。

第一，执行成本大幅下降。Bun 从 Zig 重写成 Rust，约一百万行代码，几乎全部由 Claude 智能体完成，用了几天，而非几个月。而且，先别急着想到“锁定”：反方向迁移虽然没那么容易，却也从未像今天这样容易过。从 Rust 迁到 Zig，从 React 迁到 Solid，都比过去更容易。

这听起来是好消息。确实也是。当迁移需要耗费数年的人力时，成本会抑制追逐潮流的冲动。如今，各个方向的执行成本都便宜了许多，剩下的就只有理由。从表面上看，这应该让决策更依赖技术本身的价值。但如果方向由叙事决定，你就会开始理解，为什么文档里埋着的一句话，值得用一整篇文章来讨论。

第二，结论的生产已经工业化。Cognition 刚把自己的营销网站从 Astro 迁到了 Next.js。一个内容网站。几乎所有人都认为这是 Astro 擅长的场景，包括那些与这场争论毫无利益关系的人。迁移由 Devin 自己执行，并作为案例发表：智能体修改代码、测试，还录下了自己的验证过程。没有代码仓库，没有前后对照的数字，没有基准测试。最终交付的重点成了那个故事。

相信我，这种故事多得是。迁移已经成了智能体行业的一种演示类型。几周前，Theo Browne 就试图用一些很好的建议告诉我这一点。但亲身经历时，感受要强烈得多。能被演示得天衣无缝的迁移，自然会朝向智能体今天最擅长编写的技术。市场部门正在以正常工程决策从未有过的速度，批量生产“X → 主流库”的结论。

矛盾就在这里：技术栈从未如此容易受到流传结论的影响，而这些结论也从未生产得如此之快、附带的论证如此之少。

### 一份论证应该是什么样

这样的论证并非不存在，只是越来越少见。

Bun 从 Zig 转向 Rust 时，Jarred Sumner 公开解释了理由，也拿出了证据。他谈到一些缺陷类型和内存管理问题。你可以不同意他的论证，也确实有人在公开场合逐点反驳。这就是价值所在：论证可以被讨论、核查、缩小适用范围、反驳或加强。一个结论只能被重复。

再看看 TanStack 在 tanstack.com 上使用 React Server Components 的过程。这一年，他们几乎一直在和自己辩论。采用 React Server Components 时，他们写了文章，也做了测量。停止使用时，他们同样解释：什么变了，用什么替代了它，为什么在自己的具体场景下，权衡发生了反转。与此同时，TanStack Start 仍然继续把 RSC 作为可选的基础能力提供给其他人。

那篇解释转向的文章把这次决定称为“平淡无事”，这个措辞很能说明问题。围绕 React 的旗舰架构公开改变立场，却带来了理解，而没有引发一场情绪争吵。因为他们交付了分析，而非一个简单裁决。

这才是让评估进入公开记录的样子。jQuery 输给 React，靠的是几年间公开进行的技术论辩。你所尊重的每一个库，都曾赢过这样的争论，才走到今天的位置。前面描述的那套事件传播机制，没有进行这种交锋。它只保留方向，然后不断强化这个方向。

### 那份没有人发表的论证

公平地说，Cursor 从未作出一个正式裁决。先是一项“仍需仔细审查”的实验，接着是一条祝贺 Solid 2.0 RC 发布的帖子。但那条帖子仍把 signals 描述为“性能陷阱”和“意外的依赖扩散”，没有数字，没有可供讨论的具体材料，随后就直接把 React Compiler 当作解法。这不需要恶意。诊断与药方，只是来自同一个地方。

当我试着还原 Cursor 本来可以给出的理由时，事情变得有趣了。远比“性能陷阱”有趣。

帖子明确指出，智能体“很不擅长写出好的 Solid 代码”，什么东西“最后都会被意外追踪”。虽然以我这颗习惯了 Solid 的脑袋，很难想象他们到底做了什么才会变成那样，但我完全相信这件事。内化了 React 思维模型的智能体，会用写 React 的方式写 Solid，而这样写出来的 Solid 代码会很糟糕。我也见过相反的情况。区别在于：智能体写错 React 时，训练数据还能帮助它纠正；写错 Solid 时，训练数据就爱莫能助了。这完全是一场数量竞争。

但同一条帖子里，还有一个朝相反方向的决定：他们也在从 Tailwind 迁往 StyleX。这次迁移违背了数量优势。StyleX 提供的，是发现智能体错误的能力。样式有类型约束，合并顺序是确定的，凭空编造出来的类名会成为构建错误。

把两件事放在一起，可以得到一个结论：让智能体犯错的代价足够低。有两条路径——数量与验证。React 加上它的编译器，在数量上占优，在验证上或许也占优。StyleX 在数量上不占优，却在验证上明显胜出。从这个角度看，Solid 1.0 的 signals 响应式机制确实处在一个不太舒服的位置，我不会假装没有这回事。但这也恰好是 Solid 2.0 在设计上投入精力的方向。

把数量和验证当成两个维度，是一种具体、可核查、有用的分析。它能提出可检验的主张，也能给每位框架作者一个设计目标。当然，它也可能是错的。这是我根据一条没有基准测试的帖子，加上自己的推断，还原出来的解释。Cursor 实际的理由可能完全不同。

StyleX 这个决定甚至更有意思。当验证能力胜出时，智能体驱动的开发可以逆着数量优势前进。小众技术还有第二个可以努力的方向。对我来说，这算不上新发现，但实践验证了理论。

### 如果什么都不改变

顺着这套思路推到最后，除了少数例外，每一层最终都会收敛到当下最流行的方案。前端趋向 React，系统编程趋向 Rust，脚本趋向 Python，连那些只是展示页面的网站也趋向 Next.js，适不适合都顾不上了。这样形成的，是一个单一化的技术生态。它源于一个已经分不清“训练数据里更多”和“更好”的系统，而非对各个库技术价值的认真比较。

即使你喜欢 React，也应该担心。React 之所以优秀，是因为它有竞争对手。Hooks 出现时，各种组合模式正在被探索。React Compiler 的出现，部分也是在回答基于 signals 的框架多年来不断追问的问题：为什么开发者要为大范围重复渲染付出代价？React 最大的优势，一直是能够吸收外部压力，并把它转化成自身的进步。单一化的生态会让替代方案消失，也会让竞争压力消失。没有压力的生态不会一直保持优秀，它会停滞。

仍然有回去的路。团队公开分析，而非只给结论。模型厂商公开评估自己的产品。库的作者向 StyleX 学习，在验证能力上投入。其他人则在转发之前，学会区分产出与论证。最后这件事，从社交媒体诞生起，我们就一直没做好。

与此同时，我们可以继续编写规则文件、llms.txt，通过 MCP 提供文档，整理精选示例。Solid 2.0 在这些方面都做了很多，也确实很有帮助。但上下文是借来的，无法永久占有。每次会话、每个工具，都要持续注入这些材料；而与你对抗的惯性，却会自动发挥作用。

### 下一个新想法从哪里来

我想留下一个更值得深究的问题。Solid 能否生存并非这场讨论最终关心的事。我们很好，正在发布项目有史以来最大的一次更新。我们的社区认真选择了这个框架，还清楚地知道自己为什么选择它——这一点尤其重要。

问题是，下一个新想法从哪里来？

每一种产生过重要影响的范式，最初都是既有体系不擅长编写的东西。React 曾因为 JSX 被嘲笑了将近一年：把标记写进 JavaScript？你疯了吗？关注点分离怎么办？如果今天这套机制在 2013 年就已经存在，模型训练用的是满世界的 jQuery 和 Backbone，文档把大家已经在做的迁移奉为标准，结论比论证提前几个月到处传播，你觉得 React 还能走过那个阶段吗？

它靠人们在公开场合提出可以验证的理由获胜，当时的默认选择并不偏向它。我也不认为这样的机制已经消失。各个方向的迁移，都从未如此便宜。离开任何单一化生态的机会，从未如此充足。即使我们越来越少亲自参与实现，也需要继续让分析参与讨论。这样才能在了解情况的基础上作出选择，承担责任。

## 我的评论：AI 写得顺手，值多少钱

最让我在意的就是开头那句话：每一层，都可能收敛到当下最流行的方案。

我愿意把它看成一个值得警惕的反馈过程。某套技术的公开材料越多，模型越容易生成可用代码；开发者为了减少返工，更愿意选它；由此产生的新项目、教程和演示，又进一步增加它的可见度。如果后续的数据收集继续偏向这些材料，这个循环还可能被进一步强化。

这个推演有条件，也还需要证据。React、Rust、Python、Next.js 分属不同层次，面对不同的技术约束，不能凭几个迁移故事，就断言它们会占据所有场景。但作为一种选型倾向，它值得认真讨论：一个答案被不断重复之后，人很容易忘记，它原本需要理由。

### AI 的熟练程度，确实可以进入成本账

我不会因为某个方案更受 AI 欢迎，就认为选择它有问题。

如果一个团队的大部分代码都交给智能体完成，而某套技术能明显减少生成错误、审查时间和后续返工，这就是实际收益。框架本身的性能、表达能力，原本就只是选型的一部分。协作方式变了，成本结构也会变。

但这个理由需要说完整。“AI 更擅长 React”还不够。它在哪类任务上更可靠？节省了多少人工修复？为了获得这些收益，是否增加了客户端代码、部署复杂度，或者长期维护负担？

我能接受一次有具体约束的取舍：团队用可测量的成本，换取可接受的损失。只展示迁移跑通，却没有解释这些问题，就很难判断另一个项目是否值得照做。

### 迁移演示，跳过了最需要判断的部分

“把 A 改成 B”很适合演示智能体：任务边界清楚，有大量可见的代码改动，还能以构建和测试通过作为结束。

可在真正的项目里，前面还有一个决定：为什么要迁？

假设一个内容网站已经满足加载速度、内容管理和部署需求。把它完整迁进一个更复杂的框架，当然能证明工具的执行能力。至于网站是否获得了好处，还需要查看迁移前后的结果。构建通过，无法替代这份比较。

我希望看到的迁移案例，至少留下四样东西：原来的具体问题、考虑过的替代方案、前后使用同一口径的测量，以及迁移后新增的代价。即使最后结论是“性能变化不大，但团队每周能少花几小时维护”，也比一句“我们已经切换到 B”有参考价值。

### 我更看重小众技术的验证能力

原文里，Tailwind 到 StyleX 的例子很重要。它给“流行者会更流行”的判断留下了一个出口：一种技术即使没那么多示例，只要能及时指出错误，也可能适合智能体使用。

Ryan 对 Cursor 动机的解释仍然是推断。我从这个例子得到的启发，是评价工具时可以多问一句：**它能不能让 AI 尽早知道自己做错了？**

错误如果只在用户操作某条隐蔽路径时出现，修复成本通常很难控制。如果类型检查、构建错误、测试或运行时诊断能够提供清楚的反馈，智能体就有机会在交付前改正。文档里的正确示例很有用，能指出错误的反馈同样值得投入。

这也让我觉得，小众框架不必把全部精力都用来增加被模型“见过”的次数。它们还可以把接口做清楚，把错误暴露得更早，让一个不熟悉它的工具也能循着反馈完成工作。这条路是否有效，完全可以用同一批任务做比较。

### 人可以少写代码，选型理由仍然要有人负责

我赞同 Ryan 对技术生态多样性的担心，也不觉得多样性意味着每个项目都得主动选冷门框架。具体项目首先要把自己的问题解决好。

我希望保留的，是重新比较的习惯。主流方案需要说明适用条件，小众方案有机会拿出证据，已有决定也允许被新的结果推翻。这样，竞争才有内容。

当 AI 把实现成本降下来，我们本来可以更便宜地试验不同方案。如果最后只是更快地重复同一个默认答案，那很可惜。

对我而言，一次技术选型至少应该留下这样一段能被检查的话：在这些需求和约束下，我比较过哪些方案，为什么接受当前方案的代价。代码可以交给 AI 写，这段理由仍然需要自己想清楚。
