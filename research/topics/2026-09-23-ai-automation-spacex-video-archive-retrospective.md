2026 年 9 月，一条每 12 小时运行一次的本地自动化开始维护站内 SpaceX 发射视频时间线。任务需要检查 SpaceX 官方 X 账号、下载短视频、匹配 Launch Library 2 任务数据、核验发射事实、写入仓库、运行测试，再提交并推送。

最近一次成功归档留下了完整运行记录。它在 **8 分 32 秒**内完成一场历史发射的归档，调用工具 **23 次**，处理一段 **9.728 秒、4.18 MiB** 的视频，最终修改 3 个文件并推送 1 次提交。运行侧记录的 Token 总量为 **3,330,422**，其中 **3,171,328** 是缓存输入。

这组数字说明，本地 Agent 可以完成跨浏览器、外部数据源、媒体文件和 Git 仓库的闭环工作；当任务长期挂在同一个对话并定时唤醒时，上下文、界面控制和异常重试会迅速抬高资源消耗。

## 一、实测结果

统计对象是 2026 年 9 月 23 日 09:28:50 至 09:37:23 的一次成功运行。数据来自 Codex 本地任务数据库、运行日志、Git 提交和归档草稿。Token 是任务遥测口径，不等同于 API 账单，也不能直接换算成订阅费用。

| 指标 | 实测结果 | 口径 |
| --- | ---: | --- |
| 总持续时间 | 8 分 32.453 秒 | 从任务开始到完成 |
| Agent 工具调用 | 23 次 | 21 次通用工具调用，2 次浏览器控制 |
| 输入 Token | 3,326,531 | 单次运行最终记录 |
| 缓存输入 Token | 3,171,328 | 占输入的 95.33% |
| 非缓存输入 Token | 155,203 | 输入减去缓存输入 |
| 输出 Token | 3,891 | 占总 Token 的 0.117% |
| 推理 Token | 854 | 计入输出统计的推理部分 |
| 总 Token | 3,330,422 | 输入加输出 |
| 浏览器控制超时 | 2 次，共 60.119 秒 | 占总持续时间 11.73% |
| 外部数据匹配重试 | 1 次 | 首次因沙箱网络限制失败 |
| 测试 | 首轮 9 过 1 败；复跑 10 过 | 失败来自归档数量断言未更新 |

| Git 结果 | 1 次提交，1 次推送 | 提交 `ecefbc1e` |

同一任务对话在统计时已经累计 24 轮、约 2 小时 38 分钟的运行时长和 6,114 万 Token，但其中混有页面开发、文档处理和其他问答，不能全部归到 SpaceX 自动化。单次运行数据边界清晰，更适合评价这条流程。

## 二、一次归档实际经过了什么

### 1. 先检查仓库和已有记录

Agent 读取 Git 状态、归档数据、脚本和最近提交，确认目标任务尚未进入时间线，同时避开工作区中的其他未提交改动。这个步骤承担安全检查：自动化只能暂存本次新增的视频、记录和对应测试。

### 2. 尝试访问 SpaceX 官方 X 页面

流程要求视频只来自 SpaceX 官方 X 原帖，并优先选择 10 至 45 秒的发射、分离、部署或着陆片段。浏览器中已经安装“X 视频下载助手”，正常路径是在官方帖子上直接点击下载。

这次运行中，浏览器控制连续两次超时，每次约 30 秒；直接读取 X 页面又遇到 403。最终使用下载目录里已经存在的官方短视频继续处理。这个细节暴露了自动化边界：浏览器插件依赖本机登录态、可见页面和扩展按钮，云端任务无法天然复用这套状态，本地自动化也会受窗口和控制连接影响。

### 3. 读取视频元数据并匹配任务

`ffprobe` 读取到视频时长 9.728 秒，MP4 的 `creation_time` 为 `2026-08-26T15:41:46Z`。归档脚本以这个时间为线索，在前后 12 小时范围内查询 Launch Library 2。

首次查询受沙箱网络限制而失败；获得网络权限后，第二次匹配成功。候选任务是 Starlink Group 15-22，发射时间为 `2026-08-26T09:35:11Z`，视频创建时间与发射时间相差 21,995 秒，也就是 6 小时 6 分 35 秒，落在匹配窗口内。

匹配结果包括：

- 发射地点：加州范登堡太空军基地 SLC-4E；
- 火箭：Falcon 9；
- 一级助推器：B1082，第 24 次飞行；
- 载荷：27 颗 Starlink 卫星；
- 结果：发射成功，一级成功着陆“Of Course I Still Love You”无人船；
- 官方帖子：SpaceX 的 X 原帖；
- 任务数据：SpaceX 任务页与 Launch Library 2。

Agent 还生成了 5 帧接触表，目视确认画面是夜间点火升空。结构化数据解决“是什么任务”，画面检查解决“这个视频是否真的能代表任务”。

### 4. 写入归档并验证

视频体积低于站内阈值，归档脚本直接复制，没有再次转码。随后更新发射时间线和导航测试。

第一轮验证出现 1 个失败：测试仍然断言归档视频数量为 5，而新增后已经是 6。更新断言并复跑后，10 项测试全部通过，公开资源体积检查也通过。两轮测试与资源检查合计约 10 秒。

最后只暂存 3 个相关文件，生成提交 `ecefbc1e` 并推送到 `main`。推送前检查再次运行资源体积、敏感文件和 lint 验证。仓库里同期存在的其他改动没有进入这次提交。

## 三、333 万 Token 从哪里来

最终输出只有 3,891 Token，约占总量的 0.117%。资源主要花在输入侧。

### 长对话持续携带历史上下文

自动化绑定在一个持续使用的本地任务中。每次唤醒都要重新理解系统约束、仓库规则、过去对话、工具说明和前序运行结果。缓存降低了重复计算的实际成本，但运行记录仍会把缓存输入计入 Token 总量。此次输入中 95.33% 命中缓存，说明大量信息是重复上下文。

这也解释了一个看似反常的现象：8 分多钟的任务只有几千 Token 输出，却记录了 333 万 Token。数字高的主要原因是上下文体积和多轮工具往返，不能简单理解为模型“写了 333 万 Token”。

### 跨系统工作需要多次观察与确认

这条流程跨越六类对象：

1. SpaceX 官方 X 帖子；
2. 浏览器扩展和本地下载目录；
3. MP4 元数据与视频画面；
4. Launch Library 2 和 SpaceX 任务页；
5. 站内归档脚本、数据文件与测试；
6. Git 提交与远端推送。

每次工具返回都会进入后续判断。失败结果同样占用上下文：两次浏览器超时、一次网络失败和一次测试失败都引出了新的观察、修正和复跑。

### 安全约束也有成本

工作区包含其他未提交改动，自动化需要多次查看 `git status`、差异和暂存结果，防止把无关文件带入提交。事实核验也不能只依赖视频文件名，需要把时间、地点、载荷、助推器飞行次数和着陆结果逐项写入草稿，确认 `needsVerification` 为空后才允许归档。

这些检查增加了工具调用，但它们保住了两条关键边界：资料来源可追溯，Git 变更范围可控制。减少消耗时应优先压缩重复上下文和失败路径，不宜删除必要的事实与发布校验。

## 四、这条自动化创造了什么价值

### 视频从临时文件变成可检索资料

一段下载到本机的 MP4 只有画面和粗略时间。归档后，它拥有任务名称、准确发射时间、地点、载荷、助推器、着陆结果、官方帖子 URL、来源清单和站内时间线位置。读者可以按目录和里程碑浏览，搜索引擎也能理解页面中的文字信息。

### 历史追溯形成统一口径

SpaceX 发射频率高，帖子、直播、短视频和任务页分散在不同入口。逐场回溯能形成连续档案，但前提是每场任务遵守相同字段和验证规则。自动匹配与测试降低了日期写错、视频挂错任务和统计数量失真的概率。

### 一次运行留下了可改造的数据

Token、持续时间、工具调用、失败原因、视频体积和测试结果放在一起后，优化方向变得具体。浏览器控制超时占了 11.73% 的总时间；缓存输入占输入的 95.33%；最终输出只占总 Token 的 0.117%。下一轮优化应该优先处理任务上下文和工具链路。

## 五、为什么先暂停本地定时运行

每 12 小时唤醒一次的策略会占用本机任务资源，也会把越来越长的历史继续带入新一轮。没有新发射或没有合适短视频时，检查本身仍然会发生；遇到 X 登录态、扩展按钮、网络权限或下载目录变化时，自动化还可能停在本机等待。

OpenAI 的产品说明区分本地工作流与云端任务：本地工作流运行在用户设备，云端任务运行在 OpenAI 管理的环境。Work 可以按计划或触发器重复运行，但云端任务不能直接读取个人电脑文件。对于依赖本机浏览器扩展、登录态和下载目录的视频工作流，把整个链路直接搬到云端仍会缺少关键能力。

暂停是为了停止低信息密度的定时唤醒，保留已经验证过的脚本、数据结构和发布路径。后续可以在更小的上下文中按批次执行。

## 六、适合继续推进的混合方案

### 云端只负责发现候选

轻量任务定期检查 SpaceX 官方账号和发射数据，只输出候选任务 JSON：任务名、帖子 URL、发布时间、视频时长线索和是否已归档。没有新候选就立即结束，不读取仓库历史，不下载视频，不启动本地浏览器。

### 本地集中下载小视频

发现候选后再通知人工打开官方帖子，通过“X 视频下载助手”下载。一次集中处理多场任务，执行明确的媒体门槛：

- 只取 SpaceX 官方 X 原帖；
- 优先 10 至 45 秒短视频；
- 跳过完整直播和大体积视频；
- 下载前显示时长与预计体积；
- 没有合适短视频时保留候选，不强行归档。

### 确定性脚本承担重复工作

下载完成后，脚本可以自动完成 `ffprobe`、时间匹配、草稿生成、字段校验、资源体积检查和测试。Agent 只处理多候选、时间不一致、特殊纪录核验和测试失败等异常。

### 每次运行保存一行运营数据

建议新增一份不含敏感内容的运行台账，至少记录：

| 字段 | 用途 |
| --- | --- |
| `runId`、开始与结束时间 | 计算总耗时和趋势 |
| 输入、缓存输入、输出、推理 Token | 区分上下文成本与生成成本 |
| 工具调用数、失败数、重试数 | 识别不稳定环节 |
| 候选任务数、归档任务数 | 衡量有效产出 |
| 视频时长、原始体积、归档体积 | 控制媒体成本 |
| 测试首轮结果、最终结果 | 衡量返工率 |
| Git 提交 | 把运行记录与最终产物关联 |

连续积累 10 至 20 次后，可以计算每场归档的中位耗时、P90 耗时、平均非缓存输入 Token、失败率和人工介入率。届时再判断云端发现频率、批量大小和模型档位，会比只看某一次总 Token 更可靠。

## 七、当前结论

这次实践证明，本地 Agent 有能力把一个真实的视频归档任务从文件识别推进到可访问的站内资料，并完成测试、提交和推送。它也暴露了三项直接成本：长对话反复携带上下文、浏览器插件难以稳定自动控制、外部数据与本地 Git 之间需要多轮校验。

适合长期运行的形态是分层处理：云端低成本发现、本地人工确认下载、脚本完成确定性归档、Agent 处理异常。这样既保留官方视频来源和事实核验，也能减少本机常驻、空转唤醒和高 Token 上下文。

本次 333.04 万 Token 是一次运行的遥测结果，其中绝大多数为缓存输入。它适合用来定位上下文膨胀，不适合直接当作现金成本。后续评估应同时看非缓存输入、成功归档数、人工介入次数和每场任务耗时。
