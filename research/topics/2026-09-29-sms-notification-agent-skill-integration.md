> **风险与合规提示：** 场景和架构建议用于产品研究，不构成法律意见。短信业务需结合目标国家或地区、消息类型、号码资源、行业监管与供应商规则单独评估。Twilio 的具体产品范围和地区能力可能变化，接入前应以官方文档与合同为准。

## 一、结论：短信更适合作为智能体的执行能力

短信通知的规模增长，取决于它能否进入真实业务流程。单独提供“帮我发一条短信”的工具，调用频次有限，也很难证明业务价值。更有价值的产品定位，是让预约智能体、销售智能体、订单智能体、运维智能体等在关键节点调用同一套短信通知 Skill。

这套 Skill 需要完成四件事：

1. 接收结构化业务事件，例如预约即将开始、订单配送异常、客户长时间未跟进、服务器告警未确认。
2. 判断是否应该发、何时发、发给谁，以及短信是否为合适渠道。
3. 通过合规模板和通信供应商完成发送，处理频控、退订、静默时段、去重和失败重试。
4. 把送达、失败、回复和后续业务动作回写给原智能体。

短信由此成为业务智能体的“外部触达动作”。衡量单位也应从发送量转向有效动作：预约是否确认、告警是否响应、客户是否回复、订单问题是否解决。

## 二、Skill 的核心：事件、策略、发送与反馈

智能体直接接收手机号和自由文本，再自行决定发送，容易产生误发、重复发送、越权营销和敏感信息泄露。通用短信 Skill 应提供受控接口，由业务智能体提交意图和事件，通知系统负责执行。

一个基础调用可以采用以下结构：

```json
{
  "recipientRef": "customer_8f31",
  "eventKey": "appointment_20260930_1030",
  "intent": "appointment_reminder",
  "templateId": "appointment_confirm_v3",
  "variables": {
    "time": "9月30日 10:30",
    "location": "朝阳门店"
  },
  "priority": "normal",
  "expiresAt": "2026-09-30T10:30:00+08:00"
}
```

`recipientRef` 由独立的身份服务解析，业务智能体无需长期持有明文手机号。`eventKey` 用于幂等和撤销，`intent` 决定合规与频控策略，`templateId` 限制文本范围，`expiresAt` 防止过期通知继续送达。

建议提供六类原子能力：

| 能力 | 作用 | 典型调用方 |
| --- | --- | --- |
| `notify.send` | 立即发送一次通知 | 订单、告警、风控智能体 |
| `notify.schedule` | 在指定时间发送 | 预约、日程、续费智能体 |
| `notify.escalate` | 未响应时升级联系人或渠道 | 运维、客服、照护智能体 |
| `notify.cancel` | 业务状态变化后撤销待发通知 | 预约、物流、活动智能体 |
| `notify.status` | 查询送达、失败、回复状态 | 所有业务智能体 |
| `notify.consent` | 查询授权范围与退订状态 | 营销、会员、销售智能体 |

这些能力保持稳定，行业差异放在事件适配器、模板、策略和结果解释中。这样，一套底层 Skill 可以被多个智能体复用，场景团队无需重复建设短信供应商接入与合规控制。

## 三、短信通知与业务融合的优先场景

适合短信的节点通常同时具备三项特征：事件重要、时间敏感、用户可能不在应用内。短信在这些场景中承担兜底、确认或升级动作，而非替代应用内消息、邮件和即时通信。

| 智能体场景 | 触发事件 | 短信动作 | 反馈闭环 | 核心指标 |
| --- | --- | --- | --- | --- |
| 预约与日程 | 预约创建、临近、改期、取消 | 提醒时间地点，提供确认或改期入口 | 确认、改期、取消回写日历和门店系统 | 到场率、爽约率、人工确认量 |
| 销售与 CRM | 新线索、承诺回访、报价到期、客户沉默 | 发送身份明确的跟进或材料入口 | 回复和点击进入线索时间线，决定下一步跟进 | 首次响应时间、有效回复率、成交转化 |
| 订单与售后 | 发货、配送异常、退款进度、售后补充材料 | 告知状态和可执行动作 | 用户选择、补件或客服介入回写工单 | 问题解决时长、咨询量、退款完成率 |
| 运维与安全 | 告警达到阈值、值班人未确认、登录风险 | 发送告警摘要并按规则升级 | 确认、接单、恢复状态进入事件系统 | 确认时长、恢复时长、无效告警率 |
| 出行与车辆 | 航班变化、接送临近、充电完成、车辆异常 | 提醒变化、集合点或处理入口 | 确认与处理状态回写行程或车辆系统 | 延误响应率、超时占用、服务完成率 |
| 合同与账务 | 签署临近、付款节点、发票状态 | 发送节点提醒和安全入口 | 签署、付款、开票结果回写业务系统 | 逾期率、完成周期、人工催办量 |
| 公共服务 | 材料补正、办理进度、证照到期 | 说明事项、期限与官方入口 | 补正或办理结果回写事项系统 | 办结率、逾期率、窗口咨询量 |

首批落地宜选择“事件清楚、结果可观测、用户已有关系”的场景。预约提醒、销售承诺跟进和运维告警升级分别覆盖消费服务、企业经营和内部生产系统，也能检验定时、回复、升级、撤销等关键能力。

### 场景 Skill 不只是文案模板

“预约提醒 Skill”应包含预约状态机、提醒时点、取消规则和确认结果映射；“告警升级 Skill”应包含严重级别、值班表、超时阈值和升级链路。只有短信文案的模板库很容易被复制，也难以形成长期使用。

可复用场景包至少包括：

- 业务事件定义与字段映射；
- 默认发送策略、频控和静默时段；
- 短信模板与变量白名单；
- 回复关键词或短链接动作；
- 送达、失败、回复后的工作流；
- 场景级指标和审计记录。

## 四、集成到其他智能体应用的参考架构

```text
业务系统 / 传感器 / 日历 / CRM
              ↓ 业务事件
          领域智能体
              ↓ 通知意图
   身份解析 + 授权与通知策略
              ↓ 允许执行
          短信通知 Skill
              ↓
       国内外通信供应商
              ↓ 回执 / 回复 / 点击
        事件总线与审计日志
              ↓
          领域智能体继续执行
```

### 1. 事件适配层

通过 API、Webhook、消息队列或连接器接收 CRM、ERP、日历、工单、监控平台和物联网设备的事件。适配层把各系统字段转换为统一事件，例如 `appointment.updated`、`order.delivery_failed`、`alert.unacknowledged`。

### 2. 领域智能体

领域智能体理解业务状态，决定希望实现的结果，例如“在就诊前一天取得确认”或“十分钟内让值班人员接单”。它提交通知意图，不直接控制供应商接口。

### 3. 通知策略层

策略层检查接收者身份、授权范围、消息性质、静默时段、频率、重复事件和敏感字段，并选择短信、应用推送、邮件或人工电话。营销、服务、安全验证等意图应使用不同规则和发送通道。

### 4. 通信执行层

短信 Skill 统一不同供应商的模板、签名、发送、状态回执、上行回复、限流和故障切换。企业可以按国家、成本、到达率和监管要求配置供应商，无需改动每个领域智能体。

### 5. 结果回流层

供应商回执和用户回复转换为统一事件，例如 `notification.delivered`、`notification.failed`、`recipient.confirmed`。领域智能体据此停止提醒、切换渠道、创建工单或通知人工处理。

### 6. 记忆与审计层

长期保存的内容应以通知偏好、授权证据、事件摘要和执行结果为主。明文手机号、完整短信正文和业务敏感字段设置更短的保留期与更严格权限。审计日志记录哪个智能体、基于什么事件和策略发出了通知。

## 五、Twilio 的路径：从短信 API 到智能体通信基础设施

Twilio 的产品演进值得参考，因为它没有把智能体能力压缩成一个“发短信工具”，而是把通信通道、会话、上下文、事件和合规拆成可组合的层。

### 1. Programmable Messaging 与 Messaging Services：负责可靠发送

Programmable Messaging 提供短信等消息通道的 API。Messaging Services 在其上管理发送号码池、状态回调、入站消息和部分合规配置。业务应用调用统一接口，底层可根据国家、号码类型和发送策略选择具体发送者。

这一层对应短信 Skill 的供应商驱动与执行能力，重点是稳定接口、送达状态、重试、号码和模板治理。

### 2. Conversation Orchestrator：把跨渠道互动放进同一会话

Twilio 在 2026 年发布的 Conversation Layer 中，用 Conversation Orchestrator 把语音和消息互动关联为持续会话，并管理自动化与人工坐席之间的转接。短信不再是孤立调用，而是客户关系中的一个接触点。

对国内产品的启发是：通知的上下文需要独立于发送渠道。用户从短信进入小程序、App 或人工客服后，订单号、预约状态和前序动作仍应连续，避免重复描述问题。

### 3. Agent Connect：让不同框架的智能体接入通信通道

Agent Connect 是 Twilio 的开源智能体中间件。官方将其定位为模型和运行时中立的连接层，智能体可以继续运行在自己的模型、框架和基础设施上，再通过 Agent Connect 接入 Twilio 的语音、SMS、WhatsApp、RCS 和 Chat 等通道。SMS 通道通过 Conversation Orchestrator 的 Webhook 连接智能体。

这说明短信 Skill 无需绑定某一种大模型或智能体平台。更合适的产品边界是：定义稳定的工具协议、事件协议和权限策略，为不同智能体运行时提供适配器。

### 4. Conversation Memory 与 Conversation Intelligence：补充上下文和实时判断

Conversation Memory 汇总跨渠道客户信息和历史互动，为模型提供可用上下文；Conversation Intelligence 对实时会话执行转写、情绪、意图或升级判断，并触发后续动作。二者使通信结果可以继续驱动业务流程。

短信通知 Skill 可以先实现较轻的记忆：用户偏好、授权、最近事件、已发送次数、确认结果。只有明确业务需要时，才扩大到完整会话内容，降低数据暴露和存储风险。

### 5. Event Streams：把通信结果送回业务系统

Twilio Event Streams 提供统一、近实时的异步事件流，可把 Messaging、Voice、TaskRouter 等产品事件发送到 Webhook、Amazon Kinesis 或 Segment。官方说明其投递语义为至少一次，因此消费方需要幂等处理。

短信 Skill 同样应把送达、失败、回复和退订作为一等事件。智能体只有收到结果，才能判断任务是否完成；单次 API 返回“已受理”不能代表用户已经收到或采取行动。

### 6. 合规能力产品化

Twilio 的 Compliance Toolkit 把静默时段、号码重新分配检查、退订与同意管理放进发送流程，并通过 `messageIntent` 区分必要消息和非必要消息。Advanced Opt-Out 将 STOP 等退订结果通过 Webhook 返回应用。官方同时说明，Compliance Toolkit 当前仅支持发送至美国号码的英文 SMS，客户仍需自行承担适用法律下的合规责任。

可借鉴的重点是把合规做成机器可执行的策略与接口。每个业务智能体自行理解法规和供应商规则，会造成标准不一，也难以审计。

## 六、适合国内产品的三层 Skill 体系

### 第一层：短信通知核心 Skill

这一层由平台统一维护，提供身份解析、授权检查、频控、静默时段、模板渲染、发送、回执、回复、退订、审计和供应商切换。它面向其他 Skill 和智能体，不直接表达行业业务。

### 第二层：场景 Skill

围绕业务结果封装工作流，例如预约确认、线索跟进、订单异常、告警升级、续费提醒。场景 Skill 调用核心短信能力，同时管理领域状态和下一步动作。

### 第三层：业务连接器

连接器负责接入企业已有系统，例如企业微信、飞书、钉钉、Salesforce、HubSpot、日历、工单、监控平台、门店 SaaS 和行业 ERP。连接器越丰富，短信通知越容易进入存量工作流。

三层分离后，可以独立更换通信供应商、更新合规规则、增加新场景或适配新的智能体框架。产品增长也从逐个开发短信功能，转向复用核心能力和分发场景包。

## 七、落地顺序与商业化

### 阶段一：完成可控发送闭环

- 建立统一事件、通知意图和状态模型；
- 接入至少一家短信供应商及状态回执；
- 上线身份引用、模板白名单、幂等、频控、静默时段和审计；
- 支持定时、撤销、失败重试与退订；
- 提供一个通用工具协议，供不同智能体平台调用。

### 阶段二：验证三个场景 Skill

- 预约确认：验证定时、改期、取消和到场结果；
- CRM 跟进：验证授权、回复、点击和人工接管；
- 告警升级：验证优先级、确认、超时和多级升级。

这三个场景能覆盖面向消费者、面向客户经营和企业内部流程，并形成清晰的效果对照。

### 阶段三：支持双向会话与多渠道编排

把上行短信回复转换为业务事件，并在短信、应用推送、邮件、即时通信和人工电话之间执行渠道策略。上下文和任务状态在渠道切换后继续保留。

### 阶段四：形成场景与连接器生态

允许行业服务商开发受审核的场景 Skill、模板和连接器。平台提供权限、测试、版本、计费和审计能力，企业可以安装后配置，而无需从底层 API 开始开发。

商业模式可以包括：

- 通信量与号码资源费用；
- 按有效通知、工作流执行或智能体席位收费；
- 企业版策略、审计、私有模板和供应商路由；
- 行业场景包与连接器订阅；
- 实施、迁移和合规咨询服务。

只按短信条数收费容易鼓励过量发送。更健康的定价和产品指标应同时关注业务完成率与用户打扰成本。

## 八、如何判断规模是否健康

建议把北极星指标设为“由通知促成的有效业务动作”，并配套以下指标：

| 指标类型 | 建议指标 |
| --- | --- |
| 结果 | 预约确认率、告警接单率、订单问题解决率、线索有效回复率 |
| 效率 | 每个有效动作所需短信数、人工催办减少量、平均响应时间 |
| 可靠性 | 送达率、回执延迟、重复发送率、过期消息率、供应商故障切换成功率 |
| 体验 | 退订率、投诉率、静默时段违规率、单用户触达频次 |
| 合规 | 无授权发送率、敏感字段拦截率、审计完整率、删除请求完成时长 |

规模增长应来自更多业务流程采用和更高任务完成率。单纯提高发送频次，通常会带来退订、投诉和通道质量下降。

## 九、安全与合规边界

中国境内落地需要重点处理服务类短信与商业性短信的区分、发送主体识别、用户同意、退订、频次时段以及记录留存。2026 年 5 月 1 日起施行的《通信短信息服务管理规定》要求商业性短信息具有用户同意或请求的证据，明确发送者身份并提供便捷有效的拒绝方式；服务类与商业性短信息端口不得混用，相关发送记录、同意凭证等需要按规定留存。

《个人信息保护法》要求处理个人信息具有明确、合理目的并限于最小范围。利用自动化决策进行信息推送和商业营销时，应提供不针对个人特征的选项，或者便捷的拒绝方式。医疗健康、金融账户、精确位置、未满十四周岁未成年人信息等属于敏感个人信息，短信正文和智能体上下文应尽量避免直接暴露。

产品层面至少需要以下控制：

- 业务智能体使用接收者引用，不默认获得明文手机号；
- 营销、服务、安全验证使用不同意图、模板和通道策略；
- 发送前执行授权、频控、静默时段、去重和敏感字段检查；
- 链接使用短时效、一次性或登录后可见机制，短信不直接承载完整敏感信息；
- Webhook 验签，回执消费保持幂等，供应商凭证隔离并定期轮换；
- 保留授权、策略决策和执行审计，按法定与业务需要设置删除期限；
- 高风险场景设置人工审核、升级或二次确认。
