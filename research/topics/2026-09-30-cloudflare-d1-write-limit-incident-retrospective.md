## 一、先给结论

2026 年 9 月 30 日上午，2aran.com 使用的 Cloudflare D1 免费写入额度被提前耗尽。最先暴露问题的是 X 自动发布，随后舆情采集、互动机器人和站内自动化告警也开始失败。

截至当日约 14:00，Cloudflare 账户面板显示：

- 当日已写入 **177,320 行**，免费额度为 **100,000 行**；
- 当日已读取约 **285 万行**，尚未触及每日 500 万行读取额度；
- `tuaran-me` 最近 24 小时写入曲线约 **195,560 行**，已经足以单独解释账号级超限；
- 错误信息明确写着：`Your account has exceeded D1's free tier daily row write limit`。

Cloudflare 的计费口径按数据库实际读取和写入的行数计算。`INSERT`、`UPDATE`、`DELETE` 都会计入写入量，修改索引列还会增加索引写入。免费版当前提供每日 10 万行写入额度，并在 UTC 00:00 重置。[Cloudflare D1 Pricing](https://developers.cloudflare.com/d1/platform/pricing/)

现有证据支持五点判断：

1. **燃币固定总量迁移是最可能的触发点。** 它在额度耗尽前进入生产时间窗口，包含全量余额重算和历史流水聚合。
2. **燃币日常流水与舆情采集是主要持续写入项。** 两者在查询洞察里的可见写入量都高于在线人数。
3. **在线人数设计确实过于频繁。** 它放大了日常消耗，但最近 24 小时约 2,090 行的可见写入无法单独解释 17 万行超额。
4. **X 自动发布基本是受影响方。** 每次任务只更新少量素材和运行状态，却因为共享账号额度而无法继续。
5. **告警链路与业务数据库共用 D1，导致故障发生后连告警也写不进去。** 这是本次事故暴露出的另一处结构性问题。

## 二、额度在什么时候耗尽

Cloudflare 免费额度按 UTC 自然日计算。北京时间 9 月 30 日 08:00，新的日额度开始计算。

关键时间线如下：

| 北京时间 | 事件 | 结果 |
|---|---|---|
| 08:00 | D1 免费日额度重置 | 当日重新获得 10 万行写入额度 |
| 09:08 | 舆情采集 | 成功 |
| 09:45 | 舆情采集，处理 99 条内容 | 成功 |
| 09:49 | 燃币固定总量升级提交进入主分支 | 包含 `0100_fixed_ranbi_supply.sql` |
| 10:42 | 下一轮舆情采集 | HTTP 500 |
| 10:43 | 失败告警重试 | 三次均收到 D1 日写入超限错误 |
| 11:25 起 | X 自动发布陆续失败 | 素材状态与告警无法正常写入 |
| 13:58 | 高频在线人数与 X 发布降级修复推送 | 当日已消耗额度无法恢复 |

09:45 到 10:42 是目前能确定的额度耗尽窗口。GitHub Actions 的失败日志给出了完整错误，排除了 X API、DeepSeek 模型、定时器漏跑等早期猜测。

Cloudflare 从 2026 年 9 月 1 日起调整免费版行为：账号超过每日行读取或行写入上限后，后续 D1 查询会失败，需要升级套餐或等待下一次 UTC 00:00 重置。[Cloudflare D1 Changelog](https://developers.cloudflare.com/changelog/product/d1/)

## 三、哪些操作消耗了写入额度

### 1. 一次性燃币迁移

`0100_fixed_ranbi_supply.sql` 把原有燃币系统升级为固定 2,100 万总量，并建立储备池、黑洞账户、转账表和触发器。最重的两段 SQL 是：

```sql
UPDATE user_points
   SET balance = COALESCE(
     (SELECT SUM(pl.delta)
        FROM point_ledger pl
       WHERE pl.user_id = user_points.user_id),
     0
   ),
   updated_at = 1790730000000;

INSERT OR IGNORE INTO user_points (user_id, balance, updated_at)
SELECT user_id, SUM(delta), 1790730000000
  FROM point_ledger
 GROUP BY user_id;
```

第一段会更新 `user_points` 的每一行，即使某个用户余额原本就是正确的。第二段需要扫描并聚合整张历史流水表。事故排查时，一条后台查询对 `point_ledger` 的四次扫描合计读取约 34.62 万行，折算后可知表内约有 **8.65 万条历史流水**。

迁移具体写入了多少计费行，Cloudflare 面板没有给出可公开导出的逐语句账单。三项证据仍然很集中：

- 时间窗口吻合：迁移版本进入主分支后不到一小时，定时任务开始收到配额错误；
- 量级吻合：最近 24 小时总写入约 19.56 万行，常规线上查询面板能解释的写入明显更少；
- SQL 行为吻合：全量 `UPDATE` 会让历史存量直接转化为当日写入量。

因此，“批量迁移触发额度耗尽”是当前最有证据支持的解释。精确到每一行的归因仍需 Cloudflare GraphQL Analytics 或迁移执行结果中的 `rows_written` 元数据补齐。

### 2. 燃币、签到与资源解锁

查询洞察显示，最近 24 小时里，燃币相关的主要写入至少包括：

| SQL 类别 | 可见写入行数 |
|---|---:|
| `point_ledger` 通用流水 | 约 4,650 |
| 两类 `user_points` 余额更新 | 约 3,190 |
| 解锁消费流水 | 约 1,520 |
| `resource_unlocks` 权益记录 | 约 1,330 |

一次签到或资源解锁会经过转账、余额、兼容流水和权益记录。相关表还有主键、唯一索引和普通索引，所以一次用户动作可能对应多行计费写入。

这种写放大在正常流量下可以接受，迁移与回填需要单独预算。把 8 万多条历史流水纳入一次生产迁移，会立刻改变风险等级。

### 3. 每小时舆情采集

`public-opinion-collect` 每小时抓取 AIHOT、科技媒体 RSS 和 Hacker News，并对已有内容执行 upsert。最近 24 小时，该 SQL 的查询洞察记录为：

- 执行约 1,449 次；
- 写入约 5,880 行。

`public_opinion_posts` 有三个二级索引。每次更新内容行时，索引维护会继续增加写入量。09:45 的一次成功任务处理了 99 条内容；当来源集合稳定时，大量已存在的内容仍会被按小时更新 `collected_at` 和其他字段。

这项任务适合改成“内容发生变化才更新”，并减少只为证明存活而改写时间戳的操作。

### 4. 在线人数心跳

9 月 29 日上线的在线人数功能最初挂在所有公开页面：

- 页面可见时立即请求；
- 每 60 秒发送一次心跳；
- 标签页重新聚焦时再次请求；
- 每次请求执行 upsert、过期记录清理和在线人数统计；
- `last_seen` 上存在二级索引。

最近 24 小时，旧 upsert 执行约 1,020 次，写入约 2,090 行。它是确定存在的低价值高频写入，却没有达到本次事故的主要量级。

修复后的策略已经收紧：在线人数只在首页运行，浏览器心跳改为 10 分钟，同一访客至少间隔 8 分钟才允许更新，并移除每次请求都执行的过期记录删除。

### 5. 其他写入

查询洞察里还能看到：

- API 限流计数约 935 行；
- DeepSeek 任务记录约 585 行；
- 有效阅读事件约 400 行。

这些功能单独看都不大，但它们和迁移共享同一个账号级额度。把数据库拆成多个 D1 实例也不会获得多份免费日额度，因为账单与限制按 Cloudflare 账号汇总。[Cloudflare D1 Billing](https://developers.cloudflare.com/d1/observability/billing/)

## 四、为什么最先看到的是 X 自动发布失败

X 自动发布需要从 D1 取得素材、获取租约、更新发布状态并记录任务结果。它每次只写少量行，依赖链却很长：

```text
GitHub Actions
  → 站内发布 API
  → D1 素材租约与状态
  → DeepSeek / 新闻源
  → X API
  → D1 结果与告警
```

D1 配额在链路前半段耗尽，后面的模型调用与 X 发布不会发生。自动化页面只看到“有一段时间没有自动发”，根因藏在共享基础设施里。

失败告警也调用站内 API，并尝试把通知写入 D1。业务写入失败后，告警写入使用同一份配额继续失败，GitHub Actions 日志最终成了唯一可靠证据。故障通道必须和被监控资源保持足够的故障隔离。

## 五、已经做了哪些修复

### 在线人数降频

全站一分钟心跳已经改成首页十分钟心跳，服务端再加八分钟写入闸门。在线人数只是装饰性近似值，不值得挤占内容发布和自动化任务的写额度。

### X 发布增加降级路径

X 自动发布已经补充 DeepSeek 模型降级选择，并改善素材存储不可用时的错误识别。它无法绕过账号级 D1 硬限制，但可以避免模型名称变化或单一素材步骤故障把整个任务拖死。

### 保留原始失败证据

GitHub Actions 的 HTTP 状态、响应正文和运行链接继续保留。以后站内告警写入失败时，排查仍能从执行端找到原始错误。

这些修复会降低明天起的日常写入。当天已经计入的 17.73 万行无法撤回，只能等待下一次 UTC 日界线重置。

## 六、迁移流程需要怎样改

### 1. 迁移前先算行数

涉及存量表的 `UPDATE`、`DELETE`、`INSERT ... SELECT`，上线前至少执行三类只读检查：

```sql
SELECT COUNT(*) FROM user_points;
SELECT COUNT(*) FROM point_ledger;
SELECT COUNT(*)
  FROM user_points up
 WHERE up.balance <> COALESCE(
   (SELECT SUM(pl.delta) FROM point_ledger pl WHERE pl.user_id = up.user_id),
   0
 );
```

第三条比“更新所有用户”更重要。它给出真正需要修复的行数，迁移可以据此增加 `WHERE` 条件，只写有差异的数据。

### 2. DDL 与数据回填分开

建表、建索引和建触发器可以作为结构迁移。历史余额重算属于数据任务，应当独立执行、记录进度并支持暂停。免费额度下，较大的回填可以按主键或用户 ID 分批跨日完成。

### 3. 用执行结果记录真实成本

D1 的查询响应会返回 `rows_read`、`rows_written` 等元数据。迁移脚本应把每批结果写进 GitHub Actions 日志或外部日志系统，至少包含：

- SQL 名称与迁移版本；
- 本批处理的业务行数；
- D1 返回的读取、写入行数；
- 批次开始、结束与失败位置。

这样可以直接回答“哪条迁移写了多少行”，不用在故障后根据曲线倒推。[Cloudflare D1 Metrics and Analytics](https://developers.cloudflare.com/d1/observability/metrics-analytics/)

### 4. 给关键任务预留写入预算

免费版每天 10 万行，不能全部交给后台采集与批处理。可以先按用途划分软预算：

| 用途 | 建议每日上限 |
|---|---:|
| 登录、评论、燃币与资源权益 | 25,000 |
| 内容发布与 X 自动化 | 10,000 |
| 舆情、RSS 与分析采集 | 20,000 |
| 阅读统计与在线人数 | 5,000 |
| 迁移与紧急操作保留 | 20,000 |
| 安全余量 | 20,000 |

这是站点内部软预算，与 Cloudflare 的产品限制无关。某一类接近上限时，应优先暂停装饰性统计和可补跑采集，保留发布、登录和权益链路。

### 5. 告警不要依赖同一写配额

自动化失败时，GitHub Actions 可以直接调用外部通知通道，或只依赖 GitHub 原生失败通知。站内通知可以继续保留，但不应成为唯一告警出口。

## 七、这次事故留下的工程结论

D1 免费版足够承载个人站的日常事务，前提是高频统计、批量回填和核心业务采用不同的成本纪律。

这次事故里，真正危险的操作只是一条看起来合理的全量 `UPDATE`。历史数据规模已经从“个人站可以忽略”增长到“必须先算成本”。数据库迁移从此需要和功能代码一样接受评审、测试、预算和回滚设计。

在线人数的降频仍然值得做。它消除了一个会随流量线性增长的写入源。更关键的改进是建立迁移前估算与执行后记账，下一次看到 8 万行历史表时，系统会在运行 SQL 之前给出明确警告。
